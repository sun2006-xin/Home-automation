# 08 · 市场方案与落地研究

> 本文是 docs/07 的详细版。07 给结论，08 给证据与实现细节。
> 研读对象：米家、华为鸿蒙智家、Aqara、涂鸦、KNX、Matter/Thread，以及六起真实翻车案例与一条智慧养老赛道。

## 0. 先给一句总纲

这六条路线表面上在比参数（连多少设备、延迟多少毫秒、支持多少协议），实际上各自都在回答同一个问题：

> **断网之后，这个家还能不能住？**

答案的分歧，就是所有技术选型分歧的源头。带着这句话读下面的每一节，会发现每个品牌的设计选择都变得"理所当然"。

## 1. 全景对比

| 体系 | 拓扑 | 中枢在哪 | 断外网后 | 生态开放性 | 成本量级 | 主战场 |
|---|---|---|---|---|---|---|
| **米家** | WiFi 直连 + BLE/Zigbee 经网关 | 中枢网关（主/备/从） | 本地自动化照常 | 开放（9000+ 企业接入） | 低 | 后装零售、单品 |
| **华为鸿蒙智家** | **PLC-IoT 电力线** + WiFi 双网 | 智能主机（家庭大脑） | 断网不断联（PLC 99.99%） | 半开放（HarmonyOS Connect） | 极高（10 万起） | 前装大宅、地产 |
| **Aqara** | Zigbee 3.0 + Thread + WiFi 多协议 | Hub M3（Edge 本地） | 本地自动化照常 | 最开放（Matter Bridge） | 中 | 后装 + 轻前装 |
| **涂鸦** | WiFi / BLE / Zigbee 经网关 | 云端为主 | 基本瘫痪 | 白牌开放（OEM/ODM） | 极低 | 白牌、代工、地产配套 |
| **KNX** | 双绞线总线，**去中心化** | 无中心（分布式智能） | **完全照常，网关坏了也不影响** | 最开放（500+ 厂商互操作） | 高（800–1500 元/㎡） | 别墅、酒店、机场 |
| **Matter/Thread** | Thread mesh / WiFi + Border Router | 生态平台（Apple/Google/SmartThings） | 本地可控 | 标准开放 | 中 | 新建、跨品牌 |

**一句话概括各家的赌注**：

- 米家赌「规模和便宜」→ 所以用 WiFi + 云，靠体量摊平体验问题
- 华为赌「有线永远比无线稳」→ 所以自研 PLC，卖整体方案
- Aqara 赌「做桥比做平台活得久」→ 所以全协议 + Matter Bridge
- 涂鸦赌「我不做品牌，我做水电」→ 所以云为中心 + 白牌
- KNX 赌「智能应该成为建筑的一部分」→ 所以去中心化 + 30 年寿命
- Matter 赌「标准能终结分裂」→ 所以做应用层，不管底层用什么射频

## 2. 米家（小米）

### 2.1 三层架构

```
小米 AIoT 云（账号、远程中转、OTA、语音、数据）
        ↕
中枢 / 网关层（主中枢 / 备中枢 / 从网关 / 盲网关）
        ↕
终端设备（WiFi 设备 / BLE 设备 / BLE Mesh 设备 / 存量 Zigbee 设备）
```

### 2.2 四种网关身份 —— 最值得学的一处设计

| 身份 | 能力 | 断外网后 |
|---|---|---|
| **主中枢** | 本地自动化核心。规则**存在本地**，通过局域网或蓝牙调度设备，支持本地 App 控制 | 照常 |
| **备中枢** | 主中枢断电后**自动重新选举**，接管其工作 | 接管后照常 |
| **从网关** | 接受中枢调度，其子设备纳入中枢系统 | 照常 |
| **盲网关** | **只和云端通信**，不接受中枢调度 | **子设备全部失效** |

米家官方文档的原话是：*"对于有中枢设备的家庭，建议关闭盲网关的网关功能。"*

**这是整份调研里最有价值的一条反面教材。** 它精确描述了"只会连云、没有本地通道"的设备是什么下场——**盲**。所以这叫盲网关，不是网关。

> **直接推论**：任何节点如果只有"连云"一条路，它就是个盲网关。所以我们的节点必须有 BLE 直连 / WiFi AP / 局域网 broker 至少一条本地通道。**这不是锦上添花，这是"能用"和"能用十年"的分界线。**

### 2.3 通信选型矩阵

| 技术 | 米家的用法 | 为什么 |
|---|---|---|
| **WiFi** | 常供电设备：空调、吸顶灯、摄像头、扫地机 | 带宽大、直连路由器、不需网关 |
| **BLE** | 电池设备：传感器、门锁、手环 | 极低功耗；也可与手机 GATT 直连 |
| **BLE Mesh** | 灯、开关、插座（泛洪 + 中继） | 大量低功耗设备组控，可中继补覆盖 |
| **Zigbee** | 存量产品，**官方已不再推广** | 生态老化，传感器品类改推 BLE |

**关键认知**：一颗 2000mAh 电池跑 WiFi 上报，大概 3–7 天没电；跑 BLE + 深睡能撑一年。
所以"给每个电器装 WiFi"这个方案，**只对常供电设备成立**。

> **对本项目的约束**：我们的 C3 节点目前全部假设"常供电"（电机、灯、风扇本来就要插电）。将来若加电池传感器，必须切 BLE + 深度睡眠，不能沿用同一份固件。

### 2.4 MIoT-Spec：用 ID 描述设备能力

米家把设备抽象成四层：

```
设备 device
 └ 服务 service (siid)
    ├ 属性 property (piid)   可读可写：on / brightness / temperature
    ├ 方法 action (aiid)     可调用：toggle / open
    └ 事件 event (eiid)      设备主动上报：按键按下 / 故障
```

一个灯 ≈ `service 2 (light)` 的 `property 1 = on`、`property 2 = brightness`。
第三方 App 不需要知道具体型号，读 spec 就知道怎么控 —— **新增品类不用改 App**。

### 2.5 miIO 局域网协议（逆向所得，官方从未公开）

| 项 | 内容 |
|---|---|
| 传输 | **UDP 54321**，无连接，一请求一应答 |
| 包头 | 32 字节：magic `0x2131` + 总长 + 设备 ID + 运行秒数 + 16B MD5 校验 |
| 载荷 | JSON-RPC：`{"id":4711,"method":"get_properties","params":[...]}` |
| 加密 | **AES-128-CBC + PKCS#7**；key = MD5(token)，iv = MD5(key ‖ token) |
| 凭证 | 每设备一个 16 字节 token |
| 握手 | 发 32 字节 `21310020` + 28×`ff`，设备回 device_id 与 uptime |
| 云 | **不是必需**。绑定账号才连云，协议本身完全本地可用 |

**两条可借鉴的细节：**

1. **用设备 ID 寻址，不用 IP。** ID 终生不变，IP 是 DHCP 给的随时会变。包头里塞 id 就是为了换网段后还能找到它。
   → 我们的 `device_id`（L01/C01）走的是同一条路。
2. **每次请求前重做握手。** 因为包头带的是"设备运行秒数"，设备重启后时间基准变了，旧 stamp 会被丢弃。
   → 经验：**设备重启后所有会话状态必须重建**，不能假设连接还有效。

**一条明确的教训**：早期固件在 hello 回复里**明文吐出 token**，导致同一局域网内任何人都能读取并控制设备。后来才改成 `ff×16` 拒绝返回。

> 所以：**永远不要在握手包里放凭证**。我们的做法更省事——不发明加密协议，直接用 MQTT over TLS + 用户名密码 + broker ACL。

### 2.6 米家的设计哲学

- **规模优先于完美**：先让 6000 个型号能连上，再慢慢优化体验
- **便宜是功能**：单品几十块，让用户"先买一个试试"
- **生态开放换体量**：9000+ 企业接入，小米只做平台和标准
- **从云走向本地**（近几年）：早期纯云，现在中枢网关强调本地自动化 —— 这是被用户骂出来的转向

## 3. 华为鸿蒙智家

### 3.1 架构：1 + 3 + N

| 层 | 内容 |
|---|---|
| **1** | 家庭大脑 = 智能主机（HarmonyOS + AI 引擎，本地计算与决策） |
| **3** | 三种交互：触控（中控屏）、语音（小艺）、无感（AI 超感传感器） |
| **N** | 十大子系统：照明、遮阳、安防、冷暖新风、网络、影音、用水、能耗、家电、家具家私 |

主机分档：X2 Pro（级联支持 **2500 个设备**）、X2（600 个）、SE（中小户型前装）、EZ（后装全户型）。

### 3.2 核心赌注：PLC-IoT 电力线载波

| 项 | 说明 |
|---|---|
| 原理 | 控制信号加载到**电力线**上传输，"有电即有网" |
| 通信成功率 | 宣称 **99.99%** |
| 布线成本 | 比传统总线方案省约 **38%** |
| 施工门槛 | **电工即可完成组网**，不需要专业弱电工程师 |
| 对比 | 官方说法是 KNX/Zigbee 存在"部署难度大、成本高、稳定性差" |

**这个选择的聪明之处**：它绕开了"要不要预埋专用线"这个死结。KNX 要布绿色双绞线，无线怕干扰——PLC 说"电线本身就是网线"。对装修队来说，这是巨大的人力成本优势。

### 3.3 价格与定位

- 100㎡ 起：**¥99,999 起**
- 200㎡ 起：**¥149,999 起**
- 含主机 + PLC 组件 + WiFi 6+ 组件

这是**卖系统，不卖单品**。它面向的是"装修阶段就要定下来"的客户。

### 3.4 它的想法

> 智能家居的瓶颈不是单个设备好不好用，而是**整屋的确定性**。所以我不卖你一个开关，我卖你一整套不会掉线的骨架。

### 3.5 但它的教训也很贵

线下落地里，**"开发商全小区统一装华为有线"** 是差评重灾区（详见第 8 章 8.4）。核心问题是：有线方案一旦在前装阶段锁死，后期想改品牌、想混搭、想自己动手，成本极高。**稳定性换来了锁定。**

## 4. Aqara 绿米

### 4.1 多协议网关（Hub M3）

| 能力 | 规格 |
|---|---|
| 协议 | Zigbee 3.0 + Thread + WiFi（2.4/5GHz）+ 以太网 PoE |
| 容量 | 最多 **127** 个 Zigbee/Thread 子设备 |
| 本地存储 | **8GB 端到端加密**，存设备列表、配置、自动化规则 |
| 本地自动化 | Edge Hub 能力，断网、甚至断中枢本身仍可运行 |
| 供电冗余 | PoE + USB-C 可接移动电源当 mini-UPS |
| 隐私 | 刻意**不装麦克风和摄像头** |

### 4.2 Advanced Matter Bridging（最值得学的一招）

普通 Matter Bridge 只能把"设备"暴露给别的平台。Aqara 做的是**把私有能力也翻译过去**：

- 把 Aqara Home 里自定义的**场景**转成虚拟开关（virtual plug）
- 把**存在感应**转成 occupancy sensor
- 把摄像头的人脸检测、FP2 的跌倒检测这类"生态独有能力"，也桥接给第三方 Matter 平台
- 把用电功率触发的自动化暴露出去

> **工程上的意义**：桥接的粒度不应该是"设备"，而应该是"能力"。这条思路我们的 `_discovery` 机制可以直接用——节点声明的不是"我是窗帘"，而是"我支持 cover/set(pos)"。

### 4.3 演进路径（很聪明）

M1S → M2 → M3 三代网关，**老设备的 Zigbee 子设备可以迁移到新网关**。这让用户敢买，因为知道不会被锁死在旧硬件上。

### 4.4 它的想法

> 我不做平台，我做**最好用的桥**。你爱用 Apple Home 就用 Apple Home，爱用 HA 就用 HA，我只保证我的设备在哪儿都能用。

这是"开放"最务实的形态：**不争入口，争设备**。

## 5. 涂鸦 Tuya

### 5.1 架构：1 + X + N

| 层 | 内容 |
|---|---|
| **1** | 统一云平台（设备接入、用户管理、数据互通、跨品牌协同） |
| **X** | 6 大场景系统（照明、守护、环境、娱乐等） |
| **N** | OEM/ODM 定制：自有品牌 App、SaaS、营销闭环 |

### 5.2 商业模式才是它的核心

涂鸦不做品牌，它**卖"变成智能品牌"的能力**：

- 模组（硬件）→ 云平台 → App SDK / OEM App → SaaS → 设计施工运维工具链
- 客户是：全屋品牌商、地产科技公司、家装公司、酒店、公寓运营商
- 支持 Zigbee / WiFi / BLE / BLE Mesh / Matter / NB-IoT / 4G 多协议

### 5.3 它的想法

> 智能家居的门槛不在技术，在**从 0 到 1 做一整套品牌、云、App、售后的成本**。我把这个成本打包卖给你。

### 5.4 代价

**云为中心**。设备、App、场景全在云上，断网基本瘫痪。这是"低成本快速出货"的必然代价 —— 也是它在 C 端口碑不如米家的原因。

## 6. KNX（有线工业级）

### 6.1 技术特征

| 项 | 规格 |
|---|---|
| 标准 | ISO/IEC 14543-3、EN 50090、GB/T 20965 |
| 介质 | 专用双绞线（俗称"绿线"），总线供电 **30V DC** |
| 单线容量 | 规范允许 **256 台设备/线路**，多线路可扩展 |
| 传输距离 | 单总线约 **1000 米** |
| 拓扑 | **去中心化**：设备自带智能，不依赖中央控制器 |
| 响应 | 典型 **< 100ms**（硬件总线通信，无云往返） |
| 寿命 | 设计寿命 **20–30 年**，与建筑同周期 |
| 生态 | 500+ 厂商、8000+ 认证产品互操作 |
| 成本 | **800–1500 元/㎡**（含布线、设备、ETS 调试） |

### 6.2 它最硬的一条：中央坏了也不影响

因为 KNX 是**分布式智能**——每个执行器、每个面板自己就能工作。网关只是"翻译官"，用来对接手机 App 和 HomeKit。**网关坏了，墙上的开关照样开灯。**

对比一下：米家的盲网关、涂鸦的云、华为的主机 —— 一旦这个东西挂了，全家不同程度失能。

> 这是"去中心化"最朴素也最强的价值证明。它也是我们设计里"节点本地闭环"这条原则的工业级背书。

### 6.3 现实答案是混合

行业内普遍共识（多家集成商的公开说法一致）：

> **KNX 做主干**（灯光、窗帘、空调这类固定设备），**无线做补充**（移动面板、传感器、后期新增点位），通过 KNX/IP 网关统一管理。

理由很实在：新建/毛坯房阶段布线成本最低，一次布好能用二十年；但已装修的房子，开墙返工的成本远高于用无线。

## 7. Matter / Thread（2026 现状）

### 7.1 版本时间线

| 版本 | 时间 | 关键内容 |
|---|---|---|
| 1.3 | 2025 年底 | 摄像头、扫地机、空气质量、净化器 |
| **1.4** | 2026 年初 | 能耗管理、EV 充电桩；Thread 凭证共享改进 |
| 1.5 | 2026 年中 | 摄像头规范补齐 |
| **1.6** | 2026 年 6 月 | 未通电即可 NFC 配网；**Joint Fabric**（一设备多生态共享，状态一致）；Product Security 1.1（对齐欧盟 CRA） |

### 7.2 已经能用的

- **灯和插座**：最成熟。Philips Hue、Nanoleaf、IKEA 都能可靠跨平台配对
- **智能锁**：Schlage、Aqara U100 等，本地控制稳定，multi-admin 实用
- **温控器与温湿度传感器**：Ecobee 的 Matter 接入比老的 WiFi 集成更快更稳
- **Thread 传感器**：Eve、Aqara 的 P2 存在传感器，亚秒响应、电池 12–24 个月

### 7.3 还很痛的

| 问题 | 具体表现 |
|---|---|
| **Thread Border Router 可靠性** | r/HomeAssistant、r/SmartHome 上的**头号投诉**。设备配对成功、工作几天到几周后失联，重启 Border Router 能好一阵又复发。根因是各家固件 bug + mesh 不稳 |
| 摄像头 | 1.4 起支持但体验粗糙，多数只能原生 App 看，跨平台受限 |
| 复杂自动化 | **Matter 只管基础控制**（开/关/调光/锁/设温）。"日落后开门且已布防 → 开走廊灯到 40% + 撤防 + 开空调"这种，仍然要靠各平台自己的自动化引擎，**不通用** |
| Multi-admin 的坑 | 灯、开关没问题；摄像头/扫地机这类多子功能的设备，会出现"Apple Home 有画面但 HA 收不到移动事件"的割裂 |
| 落地速度 | 规范发布 ≠ 立即可用。2026 年中，仍有大平台在补 1.2/1.3 的支持 |

### 7.4 一个必须记住的行业教训

> **Revolv、Wink、Insteon —— 云服务关停后，用户手里的硬件直接变砖。**

这是"纯云依赖"最惨烈的结局。也是为什么 2026 年整个行业都在往"本地优先"转向。

### 7.5 对我们的意义

- ✅ 我们做的是"本地优先 + MQTT"，方向与行业共识一致
- ❌ 不做 Matter 认证（$5k–15k、6–12 周，个人项目不划算）
- ✅ 但可以**保持"能力模型"与 Matter 的 cluster/attribute 思路同构**，将来想接就能接

## 8. 落地实录：翻车案例（本章最有价值）

> 参数表看不出问题，交付现场才看得出。以下都是公开报道/业主自述。

### 8.1 龙湖御湖境 × 海尔：网关屏坏了，半年修不了

- 2025 年 12 月 31 日交付的精装房，配海尔全屋智能
- 交付后空调、照明、新风**全部无法控制**，语音、面板联网全失效
- 业主联系不上海尔，只能找物业；物业称**"海尔和地产有经济纠纷，现在没有维修"**
- 海尔上门一次，口头承诺更换网关屏，此后失联
- 同一小区**大量业主同款故障**；面板标签错乱（"按卧室灯，厕所灯亮"）
- 业主打 12345、找龙湖客服，半年无答复
- 交付时**没有任何购买记录、发票、收据**

**教训**：
1. 全屋智能的售后责任链一旦断裂（厂商 ↔ 地产），业主就是人质
2. **网关是这个系统的单点**，它坏 = 全家瘫痪
3. 交付不留凭证、不给配置文档 = 用户永远无法自救

### 8.2 万科 × 良信：三合一面板把"全屋智能"变成"全屋智障"

业主原话（小红书）：*"因为良信的存在，万科宣传的'全屋智能'瞬间变成了'全屋智障'"*

- 全屋开关**单火线**，智能开关想改双联都难
- 空调、地暖、新风全锁在良信三合一里，**没有远程控制**
- 逐项改造成本（业主实测）：
  - 给开关加零线：约 **1000 元**（专业电工）
  - 只远程控一台空调（小超人）：约 **300 元/台**
  - 7 个内机以内全控（VRF）：**1000 元以内**
  - 三合一智能旋钮：约 **400 元/只**，"奢华版"整套约 **3500 元**

**最要命的一条**：想用 VRF 完美控温，**必须把良信网关的信号线拔掉**，面板从此失去空调控制；且每个内机的网关都要拆，否则出现各种莫名其妙的问题（有业主照做后地暖调不动）。

> 这就是"私有关闭系统"的真实代价：**它不是不好用，它是无法被替换。**

### 8.3 星网锐捷 × 国贸系：想换个面板颜色都接不进米家

- 精装交付带星网锐捷系统，面板颜色不喜欢
- 想换：不兼容米家；换一套米家不算电器约 **2000 多元**
- 同小区多位业主在问"国贸金钥匙的系统怎么替换或兼容"

### 8.4 华为有线：全小区统一装，全小区统一傻眼

知乎问题"华为全屋智能有哪些必装的？"下 1.7 万浏览，高赞答案开门见山——**华为有线的全屋智能，不要碰**。业主自述：开发商精装房全小区装全套，"看房的时候大家都说好，开发商牛的，下血本"。

**问题不在华为的技术，在"统一装"这件事本身**：
- 全小区一个方案，无法按户定制
- 后期想混搭其他品牌极难
- 一旦某环节出问题，整个小区同一时间爆发

### 8.5 商家远程锁网关：尾款没付，业主摸黑 20 天

- 业主付了 85% 货款，剩 2000 元尾款
- 商家未调试完、未交权限、窗帘尺寸还做错了
- 催尾款时**网关被远程关掉**，全家灯全灭
- 报警、12315、12345 都介入

**这是最恶劣的一种设计**：系统留了"远程锁死"的后门。任何做智能家居的人都该记住——**交付权限，是交付的一部分。**

### 8.6 精装房交付的五个物理前提（装修前必须确认）

| # | 项目 | 后果 |
|---|---|---|
| 1 | 开关底盒**留零线** | 没有零线只能用单火开关：灯微亮、闪烁、兼容性差、更贵 |
| 2 | 窗帘盒**留强电** | 否则只能电池电机，续航短、充电麻烦 |
| 3 | 网线回程 + AC+AP | 全屋只靠 WiFi，设备一多就掉线 |
| 4 | 面板**刻字** | 不刻字 = 全家靠记忆，年轻人能背，**老人直接懵** |
| 5 | **复尺** | 底盒位置/高度/数量、零火线是否到位、窗帘电机电源高度、筒灯数量、灯带线路 —— 任何一项对不上，后面都是明线和补漆 |

> 这五条里，**第 4 条最容易被忽略，但对老人影响最大**。这也是为什么我们项目里 51 面板要保留实体按键与刻字。

### 8.7 一组行业数据（2026 年 3 月行业简报）

- 2025 年国内智能家居市场规模突破 **7000 亿元**，中枢控制类设备与系统集成服务约占 **26%**
- 装了全屋系统的家庭，一年后仍**每天触发场景**的比例 **> 80%**（说明不是"新鲜三天"）
- 但约 **18%** 用户"部分不满意"，集中在两项：**稳定性** 与 **售后响应慢**

> 注意：**没有一条抱怨是"功能不够多"。** 全是稳定性和服务。

## 9. 另一条赛道：智慧养老（方法完全不同）

这条赛道值得单独看，因为它的**评价标准不是"好用"，是"不能漏报"**。

### 9.1 技术核心：毫米波雷达，而不是摄像头

| 对比 | 毫米波雷达 | 摄像头 |
|---|---|---|
| 需佩戴 | 否 | 否 |
| 采集影像 | **不采集** | 采集 |
| 隐私感受 | 可接受（卧室/卫生间可装） | 强烈抵触 |
| 能力 | 呼吸、心率、体动、跌倒、离床、滞留 | 视觉识别 |

**"不采集影像"是它能进卧室和卫生间的唯一原因。** 这是产品能否落地的关键设计决策，不是技术优劣问题。

### 9.2 真实数据

| 项目 | 规模 | 效果 |
|---|---|---|
| 湖北随县均川镇福利院 | 124 台设备 / 40 位失能老人 | 跌倒报警、离床监测、睡眠分析、卫生间滞留预警 |
| 合肥蜀山区五里墩街道 | 124 户 / **233 台**雷达（覆盖 6 个社区） | 累计预警 **631 次，成功处置 631 起，险情 0 起**；其中 52 起是"身体不适卧床过久" |
| 北京海淀某方案 | 跌倒 0.5s 内响应 | 5 秒无回应 → 递进式救援：联系家属 → 呼叫 120 → **远程开门** |

### 9.3 它的真正架构：三级闭环，设备只占三分之一

```
眼（雷达感知）→ 脑（平台预警）→ 手（人力处置）
```

合肥的案例说得很清楚：他们组建了"社区工作人员 + 网格员 + 红色小管家"的专职服务队伍，**后台 24 小时值守**。

> **这是养老赛道最反直觉的一点：设备装完只完成了三分之一，剩下三分之二是"谁来看告警、谁去敲门、谁送医院"。**

纯技术的方案在这里会失败——不是识别不准，是**没人响应**。

### 9.4 对跌倒检测类项目的启示

1. **误报率是生死线**。631 次预警全部处置且 0 险情，说明阈值调得很保守；如果一天误报 20 次，护理员三天就不看了（报警疲劳）
2. **递进式响应**比"报警"有用：通知家属 → 呼叫 120 → 远程开门（临时密码，如扬州案例）
3. **不采集影像**才能进卧室
4. 老人不会用 App。"张口即来、零门槛"才是可用的交互

## 附录 · 智能开关的四种做法，与我们的位置

> 写这一节是为了回答一个问题：我们那套「日常按钮 + 三档选择器 + 位回读 + 电流检测」，是不是重复发明？
> **结论：硬件结构不是新的，但有一块空地确实少有人做——而且空着是有原因的。**

### A1. 三类现有做法

#### ① 消费级智能开关（米家 / 绿米 / 涂鸦等）

结构：**面板按键 → MCU → 继电器**。

行业资料原文：*"按面板时，信号不是直接接通电路，而是先传给模块，由模块控制继电器通断。"*

所以**"手机关不掉手动开的灯"这个问题在正规产品里不存在** —— 面板本身就不直接通断，它只是个信号源。

**代价**：MCU 死机时，面板一起废。这是通病，也是投诉高发点。

**另一个已知坑（单火线版）**：靠灯具漏电流供电，LED 会"关灯后微亮/闪烁"（俗称鬼火）。所以本项目一律零线供电。

#### ② KNX 总线执行器（施耐德 / ABB 等，工业级）

结构与家用完全不同：**面板与执行器分离**。
- 执行器（继电器模块）装在**配电箱**的 DIN 导轨上
- 面板只是传感器，通过总线发信号
- **每个通道自带手动按键 + LED 状态灯**

施耐德产品说明原文：
> *"Even without bus power, each channel can be operated manually using the built-in push buttons—ideal for system commissioning and emergency control."*

**这就是工业界的"自动/手动切换"，与我们方案同源。**
差异只在位置：它在配电箱里，需要开箱操作。

#### ③ DIY 改装（智能模块 + 传统开关并联）

很多教程推荐把智能模块和原机械开关**并联**。

**结果是手机控制失效** —— 并联是"或"逻辑，机械开关合着时，继电器断开也没用。
本项目早期版本犯过这个错，被三档选择器方案纠正。

#### ④ 机械定时开关：三档结构的几十年先例

家用机械定时器（热水器、楼道灯、鱼缸泵上那种一转就咔哒响的圆盘定时器）**几乎全都带 ON / AUTO / OFF 三档**：

| 型号 | 官方描述 | 典型用途 |
|---|---|---|
| SUL180a | `Manual Switch Mode: ON / AUTO / OFF` | 电热水器、通风扇、照明 |
| SUL-181-D | `Manual-auto-off function` | 街灯、水泵、锅炉、风扇 |
| OP-TS211.1 | `three-position manual lever for permanent on, automatic or permanent off` | 照明、加热、循环泵 |

原文：*"The three-position switch lets you choose between automatic operation, permanently on, or completely off."*

**这说明什么：**

三档不是我们发明的，是家用电气里**被验证了几十年**的成熟交互。
而且定时器用户的焦虑和我们完全一样 —— **怕到点没开，也怕一直开着不关**。所以给了强制开、强制关。

**我们的差异不在结构，在两件事：**

| 维度 | 定时开关 | 本项目 |
|---|---|---|
| 装在哪 | 配电箱 DIN 导轨 / 墙插 | **86 型墙面开关面板** |
| 谁在自动 | 机械程序盘 | **联网的 MCU + 场景规则** |
| 状态可知吗 | 只靠眼睛看旋钮位置 | **档位回读 → 上报 → App 显示"手动模式"** |

> **结论**：我们不是发明三档，是**给一个被验证几十年的老结构装上网络和状态反馈**，并搬到墙面上。

### A2. 四种方案对比

| 方案 | 日常手动 | 远程控制 | MCU 死机能开 | 断电能开 |
|---|---|---|---|---|
| 消费级智能开关 | ✅ 经 MCU | ✅ | ❌ 面板一起废 | ❌ |
| KNX 执行器 | ✅ 但要开配电箱 | ✅ | ✅ 面板手动 | ✅ |
| DIY 并联改装 | ✅ 直通 | ❌ **失效** | ✅ | ✅ |
| **本项目的三档方案** | ✅ 经 MCU | ✅ | ✅ 拨到强开 | ✅ |

### A3. 为什么厂商不做这一档

不是想不到，是**算过账**：

| # | 理由 | 说明 |
|---|---|---|
| 1 | 成本 | 多一个三档开关 + 光耦 + 2 路 GPIO，BOM 上涨 |
| 2 | 外观 | 墙面多一个旋钮，用户觉得丑、看不懂 |
| 3 | **责任** | 加这个等于**公开承认"我的产品可能死机"**，品牌不愿签这个字 |
| 4 | 安装 | 普通电工不会接三档，安装复杂度与退货率上升 |
| 5 | 需求 | 99% 用户一辈子遇不到 MCU 死机，投入产出不划算 |

> 第 3 条和第 5 条最真实。**这是"算得过账"与"算不过账"的区别，不是技术高低的区别。**
> 我们作为非商业项目，恰好可以不做这道算术 —— 这是业余项目的结构性优势，不是能力优势。

### A4. 真正不一样的地方：状态诚实

硬件结构可以对照 KNX，但有一处消费级产品普遍缺失：**档位状态是否对 App 可见**。

- 消费级产品被物理旁路后，App 仍显示"可控"，用户点了没反应，以为坏了
- 本项目把档位**回读给 MCU**，再上报 `mode:"manual_on"`，界面显示"手动模式 · 远程不可用"

**这条闭环（档位回读 → 上报 → 界面诚实告知）在消费级产品里很少见。**
它不是硬件创新，是**状态语义的完整性**。

### A5. 对外该怎么说

| 说法 | 评价 |
|---|---|
| ❌ "市面上没有这种开关" | 不成立，KNX 有手动模式，工业有转换开关 |
| ❌ "独创三档开关" | 不成立，会被直接反驳 |
| ✅ "把工业级的自动/手动/应急三段控制，用 10 元成本做到家用墙面开关上" | 准确、可辩护 |
| ✅ "消费级智能开关普遍不处理 MCU 故障层；我们补上了，并且让状态对 App 可见" | 准确、点出真正的差异 |

**一句话定位**：
> 把 KNX 的工业思路搬到家用墙面，并让"手动模式"这件事对软件可见。
> 不是发明，是有选择的移植 —— 而且移植本身也有价值。

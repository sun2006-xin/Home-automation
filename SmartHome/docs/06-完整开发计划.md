## 1. 目标与边界

### 1.1 一句话

把每个电器的驱动做成独立节点（电器 + ESP32-C3），由一个本地中枢统管，能局域网控制、能异地控制、断网仍可用。

### 1.2 六条硬指标（达不到就不算完成）

| # | 指标 | 判定 |
|---|---|---|
| 1 | 单节点自治 | 一块 C3 + 一个电器，手机 BLE 直连可完整控制 |
| 2 | 多节点并存 | ≥2 个节点同时在线，拔掉任一不影响其他 |
| 3 | 断网可用 | 拔路由器网线，局域网控制与中枢联动照常 |
| 4 | 异地可用 | 手机切 4G 可控制，延迟 < 2s |
| 5 | 差异靠配置 | 同一份 bin 烧 N 个节点，只改 `device_id` |
| 6 | 可升级 | OTA 成功，失败能回滚 |

### 1.3 明确边界

- ❌ 不用 51（51 属姊妹项目 `51-SmartHome/`）
- ❌ 不做 BLE Mesh、Zigbee（见 docs/07 调研结论）
- ❌ 不做 Matter 认证
- ❌ 不做摄像头
- ❌ 不做手机原生 App（先用 MQTT 客户端 / 网页 / PyQt5）

## 2. 硬件选型与 BOM

### 2.1 核心件

| 角色 | 型号 | 单价 | 数量 | 理由 |
|---|---|---|---|---|
| 节点主控 | **ESP32-C3 SuperMini** | ~12 元 | 3 | WiFi + BLE5 双模；4MB Flash 够 OTA；可用 GPIO 约 11 个 |
| 中枢载体 | 旧手机 / 树莓派 / OpenWrt 路由器 | 0–150 元 | 1 | 需 7×24 常开；跑 broker |
| 电平转换 | 双向 3.3/5V | ~3 元 | 2 | 仅中控形态接 51 时用 |
| 电源 | AMS1117 3.3V 模块 或 5V/2A 适配器 | ~5 元 | 3 | C3 峰值 300mA，USB 口供电常不足 |

> **为什么不用 ESP-01S**：无 BLE，做不到"手机蓝牙近场直控"；RAM 小，OTA 与 TLS 吃力。省 4 块钱丢掉一半功能，不划算。

### 2.2 被控对象（按里程碑分批买）

| 里程碑 | 电器/传感器 | 驱动件 | 估价 |
|---|---|---|---|
| M1 | 窗帘 | 28BYJ-48 + ULN2003 | ~8 元 |
| M2 | 灯 | 5V 继电器模块 或 LED 灯带 | ~4 元 |
| M3 | 风扇 | 继电器 | ~4 元 |
| M5 | 温度 | DS18B20 | ~5 元 |
| M5 | 烟雾 | MQ-2（带 DO） | ~4 元 |
| M5 | 人体 | HC-SR501 | ~4 元 |

**起步只需 3 块 C3 + 一套步进 ≈ 45 元**，其余随里程碑补。

### 2.3 节点 GPIO 规划（定稿）

| 用途 | 建议 GPIO | 备注 |
|---|---|---|
| 步进 IN1–IN4 | 4 个 | 经 ULN2003；避免用启动时会拉高的引脚（GPIO2/8/9 需谨慎） |
| 继电器 | 1 个 | 低电平触发 |
| DS18B20 | 1 个 | 4.7k 上拉 |
| MQ-2 DO | 1 个 | 数字量 |
| HC-SR501 | 1 个 | 高电平有效 |
| 本地按键 | 1 个 | 内部上拉，作"物理兜底" |
| 状态 LED | 1 个 | 板载，用于指示网络状态 |
| UART（接 51 时） | 2 个 | 交叉，注意电平 |

> ⚠️ C3 的 **GPIO8/9 是 strapping 引脚**（影响启动模式），**GPIO18/19 是 USB**（若用原生 USB 就别占）。开工前先画一张"引脚占用表"，比边写边试省事。

## 3. 架构总览

### 3.1 拓扑

```
        ┌──── 云端 broker（仅异地用，可选）────┐
        │              ↕ bridge（1 条连接）    │
   手机(4G) ──────────────────────────────┐   │
                                          ↓   ↓
        ┌──────── 本地中枢（broker + 规则引擎）────────┐
        │                                            │
   [窗帘 C3]      [灯 C3]      [风扇 C3]      [手机 局域网]
```

### 3.2 三层决策分工

| 层 | 位置 | 管什么 | 断网后 |
|---|---|---|---|
| 层一 | 节点本地 | 同节点内的联动（本机温度 → 本机风扇） | 照常 |
| 层二 | 本地中枢 | 跨设备编排、定时、场景 | 照常 |
| 层三 | 云端 | 异地访问、推送 | 失效，不影响上两层 |

**判断归节点，协调归中枢。** 节点不该知道别的节点存在 —— 这是本架构最重要的一条纪律。

### 3.3 通信四层降级（节点自动选路）

1. BLE 已连 → 走 BLE
2. WiFi AP 有客户端 → 走 AP（网页配置）
3. WiFi STA + 本地 broker 可达 → 局域网 MQTT
4. 公网 broker 可达 → 云端 MQTT
5. 全断 → 本地按键仍可控制

## 4. 节点固件模块清单

### 4.1 分层

```
app/       能力模型、状态引擎、本地规则      ← 业务
net/       WiFi / BLE / MQTT                 ← 通信
link/      link_gpio | link_serial           ← 可插拔执行层
driver/    继电器、步进、传感器               ← 外设
sys/       NVS 配置、看门狗、日志、OTA        ← 系统
```

### 4.2 模块清单

#### sys 层

| 模块 | 文件 | 接口 | 关键点 | 工时 |
|---|---|---|---|---|
| 配置 | `node_config.h` | 宏：`HOME_ID` `DEVICE_ID` `LINK_IMPL` `CAP_LIST` | **唯一的节点差异点** | 0.5h |
| NVS 存储 | `sys_nvs.c` | `uint8 Cfg_Load(cfg_t*)`<br>`uint8 Cfg_Save(const cfg_t*)` | 存 WiFi 账号、token、校准值 | 2h |
| 看门狗 | `sys_wdg.c` | `void Wdg_Feed(void)` | 主循环每圈喂一次；任务卡死自动重启 | 0.5h |
| 日志 | `sys_log.c` | `LOG_I/W/E(...)` | 分级；生产环境关 INFO 省串口带宽 | 1h |
| OTA | `sys_ota.c` | `uint8 OTA_Check(void)`<br>`uint8 OTA_Apply(const char *url)` | 版本比对 + 下载 + 校验 + 回滚 | 5h |

#### net 层

| 模块 | 文件 | 接口 | 关键点 | 工时 |
|---|---|---|---|---|
| WiFi STA | `net_wifi.c` | `uint8 WiFi_Connect(const char *ssid, const char *pass)`<br>`uint8 WiFi_IsUp(void)` | 断线自动重连，指数退避 2→4→8→…→60s | 3h |
| WiFi AP | `net_wifi_ap.c` | `void AP_Start(const char *ssid)` | 配网用；SSID 带 MAC 后 4 位 | 1h |
| BLE GATT | `net_ble.c` | `void BLE_Start(void)`<br>`void BLE_Notify(const uint8 *d, uint16 len)` | 自定义 Service + 特征：命令特征 / 状态特征 | 5h |
| BLE 配网 | `net_ble_prov.c` | `uint8 Prov_WaitCredentials(cfg_t*)` | 手机写入 SSID/密码/PASS | 3h |
| MQTT 客户端 | `net_mqtt.c` | `uint8 MQTT_Start(void)`<br>`uint8 MQTT_Pub(topic, payload, retain)`<br>`void MQTT_Poll(void)` | **LWT 必须在 CONNECT 时就设**；QoS1；自动重订阅 | 5h |
| 桥接（可选） | `net_bridge.c` | — | 仅中控形态：串口行协议 ↔ MQTT | 2h |

#### link 层（核心抽象）

| 模块 | 文件 | 接口 | 说明 | 工时 |
|---|---|---|---|---|
| 接口定义 | `link.h` | `void Link_Apply(const char *cmd, const char *arg)`<br>`uint8 Link_State(char *buf, uint8 max)` | 上层只依赖这个 | 1h |
| 直驱实现 | `link_gpio.c` | 同接口 | C3 直接驱动继电器/步进 | 3h |
| 串口实现 | `link_serial.c` | 同接口 | 与 51 发 `L01;ON` 行协议 | 3h |

| `drv_pir.c` | `uint8 PIR_Triggered(void)` | 边沿 + 保持时间 | 0.5h |
| `drv_key.c` | `uint8 Key_Scan(void)` | 消抖 + 短按/长按 | 1.5h |

| 模块 | 接口 | 职责 | 工时 |
|---|---|---|---|
| `app_cap.c` | `const cap_desc_t *Cap_List(void)`<br>`uint8 Cap_Execute(const char *cap, const char *cmd, const char *arg)` | 能力模型的执行入口 | 3h |

## 5. 能力模型（借鉴 MIoT-Spec 的简化版）

> 调研见 docs/07。米家用 `service/property` 描述设备，App 只认属性不认型号。我们做同样的事，但只用一层。
>
> ⚠️ **本章的 spec 已在 `docs/09-实现细节解剖.md` 第 7 节冻结为 v1**，含完整字段定义、`_discovery` 报文范例、HA 兼容写法与指令语义表。写代码时以 09 为准。

### 5.1 四种能力类型

| 能力 | 参数 | 适用 |
|---|---|---|
| `switch` | `on` (0/1) | 灯、风扇、插座 |
| `cover` | `pos` (0–100) | 窗帘、卷帘 |
| `sensor` | 可变键值：`t` `h` `smoke` `pir` `lux` | 各类传感器 |
| `dimmer` | `level` (0–100) | 可调灯（预留） |

### 5.2 节点声明（自动发现用）

节点上电后向 `sh/{home}/_discovery` 发布一条 **retain** 消息：

```json
{
  "v": 1,
  "id": "C01",
  "name": "客厅窗帘",
  "type": "cover",
  "cap": ["cover"],
  "cmds": ["set", "stop"],
  "fw": "0.3.1",
  "ip": "192.168.1.42"
}
```

中枢/上位机订阅这个主题就能自动列出所有设备，**新增节点不需要改中枢代码** —— 这是从米家和 Home Assistant 学来的最重要一条。

## 6. 协议规范

### 6.1 主题表（完整定稿）

| 主题 | 方向 | retain | QoS | 说明 |
|---|---|---|---|---|
| `sh/{home}/{dev}/cmd` | 中枢/手机 → 节点 | 否 | 1 | 指令下发 |
| `sh/{home}/{dev}/state` | 节点 → 全体 | **是** | 1 | 状态，retain 让新客户端立刻拿到最新值 |
| `sh/{home}/{dev}/online` | 节点 → 全体 | **是** | 1 | LWT 遗嘱：掉线自动置 0 |
| `sh/{home}/{dev}/cfg` | 中枢 → 节点 | 是 | 1 | 配置下发（上报周期、阈值） |
| `sh/{home}/{dev}/ota` | 中枢 → 节点 | 否 | 1 | OTA 指令（URL + 版本） |
| `sh/{home}/_discovery` | 节点 → 中枢 | 是 | 1 | 能力声明 |
| `sh/{home}/_scene/{name}` | 手机 → 中枢 | 否 | 1 | 触发场景 |
| `sh/{home}/broadcast` | 中枢 → 全体 | 否 | 1 | 全屋指令（全关灯） |

### 6.2 指令载荷

```json
{"v":1,"d":"C01","cap":"cover","cmd":"set","args":{"pos":50},"src":"app","ts":1730900000}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `v` | 是 | 协议版本，将来升级用 |
| `d` | 是 | device_id |
| `cap` | 是 | 目标能力名 |
| `cmd` | 是 | `set` / `toggle` / `stop` / `reboot` |
| `args` | 否 | 参数对象 |
| `src` | 否 | `app` / `rule` / `key`，便于排查"谁开的灯" |
| `ts` | 否 | Unix 秒，用于排序与去重 |

### 6.3 状态载荷

```json
{"v":1,"d":"C01","st":{"pos":50,"moving":0},"ts":1730900000}
```

**上报策略**：状态变化立即上报（去抖 200ms）+ 每 30 秒心跳一次。不要定时轮询上报 —— 那是浪费电和带宽。

### 6.4 主题里的通配符

- `+` 匹配单层：`sh/h01/+/state` → 所有设备状态
- `#` 匹配多层：`sh/h01/#` → 该家所有消息

## 7. 配网流程

### 7.1 首选：AP 配网（简单可靠）

```
1. 节点上电，未存 WiFi → 进入 AP 模式，SSID = SH-C01-A3F2
2. 手机连该热点 → 打开 192.168.4.1
3. 填写：家里 WiFi SSID / 密码 / broker 地址 / home_id
4. 节点保存到 NVS，重启，LED 慢闪 → 常亮
```

**为什么先做这个**：不需要额外 App，用浏览器就行；调试直观；失败能重来。

### 7.2 优化（可选）：BLE 配网

手机用任意 BLE 调试 App（如 nRF Connect）连上自定义 Service，往特征里写 SSID/密码。比 AP 快，但需要做 GATT 服务。

### 7.3 状态灯语义（定稿）

| LED | 含义 |
|---|---|
| 慢闪（1s） | 配网模式 |
| 常亮 | 已连 WiFi + broker |
| 快闪（200ms） | 连不上 broker，正在重试 |
| 双闪一下 | 收到指令（心跳指示） |
| 熄灭 | 深度睡眠 / 断电 |

## 8. OTA 流程

```
1. 中枢发 sh/{home}/{dev}/ota  {"url":"http://.../node-C01.bin","ver":"0.3.2"}
2. 节点比对当前版本 → 相同则忽略
3. HTTP 下载到备用分区，边下边算 SHA256
4. 校验通过 → 切分区重启；失败 → 保持原固件并上报错误
5. 重启后 60 秒内必须连上 broker，否则自动回滚
```

**必须有回滚**。节点装进墙盒之后，你没法再插 USB —— 一次刷坏就是拆墙。

## 9. 中枢方案

### 9.1 载体选择（按现有设备优先）

| 优先级 | 载体 | 装什么 | 优点 | 坑 |
|---|---|---|---|---|
| **1** | OpenWrt 路由器 | mosquitto | 本就 7×24、功耗 5W、零成本 | 要看型号能不能刷 |
| 2 | 旧手机（Termux） | mosquitto + 可选 Node-RED | 零成本、自带电池当 UPS | 安卓杀后台（需 wake lock）、长期插电电池鼓包 |
| 3 | 树莓派 Zero 2 W | mosquitto + Home Assistant | 最省心、生态全 | ~150 元 |
| 4 | 专用 ESP32-S3 | 自带 broker 固件 | 小巧便宜 | TLS 下 RAM 紧 |
| 5 | 云 broker | 巴法云 / EMQX Cloud | 无需家里设备 | 免费额度受限、断网即废 |

### 9.2 规则引擎：三选一

| 方案 | 工作量 | 灵活性 | 建议 |
|---|---|---|---|
| **Home Assistant 内置自动化** | 最低 | 高（图形化） | 先用它跑通，验证规则是否够用 |
| **Node-RED** | 中 | 极高（拖拽流） | 复杂联动时换它 |
| **自写 PyQt5 规则引擎** | 最高 | 完全可控 | 想练 Python 时再写，也是 M6 的产物 |

### 9.3 规则结构（沿用 HA 三段式）

```json
{
  "name": "烟雾报警开窗",
  "enabled": true,
  "trigger":   {"dev": "S01", "attr": "smoke", "op": ">=", "val": 1},
  "condition": [{"dev": "C01", "attr": "online", "op": "==", "val": 1}],
  "action":    [{"dev": "C01", "cmd": "set", "args": {"pos": 100}}],
  "cooldown_s": 60,
  "notify": true
}
```

必备要素：`cooldown_s`（防抖，否则烟雾抖动会疯狂开窗）、`enabled`（能一键停用）、`notify`（要不要推送）。

## 10. 安全设计

| 层面 | 措施 |
|---|---|
| 局域网 | MQTT 用户名 + 密码，禁用匿名 |
| 外网 | TLS（8883 端口），禁止明文 1883 暴露公网 |
| 权限 | broker ACL：每设备只能读写 `sh/{home}/{自己的id}/#` |
| 设备身份 | 每设备唯一 `client_id` + token，存 NVS |
| 凭证管理 | token 不进源码、不进 Git；配置存 NVS |
| 升级 | OTA 包 SHA256 校验；固件签名（可选，v8 再说） |
| 隐私 | 不上传原始传感器时序到公网，只传状态与告警 |

> **不要自己发明加密协议**。miIO 的历史教训是：早期固件在握手包里明文吐 token，全屋设备可被同网段任何人控制（见 docs/07 第 4 节）。用现成的 TLS + ACL。

app → link → driver
 ↓      ↓

## 14. 资源预算（C3 上必须心里有数）

| 项 | 预算 | 备注 |
|---|---|---|
| WiFi 协议栈 | ~50KB | 固定开销 |

| MQTT 缓冲 | 2KB | 收发各 1KB |

| BLE 协议栈 | ~30KB | 与 WiFi 共存时注意峰值 |
| 应用层 | ~10KB | |
| **合计（BLE+WiFi+MQTT 并行）** | **~130KB** | C3 有 ~400KB SRAM，余量充足 |
| 控制延迟目标 | 局域网 <300ms，远程 <2s | 从按键到动作 |
| 上报流量 | 每节点每天 < 1MB | 变化上报 + 30s 心跳 |

## 15. 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| C3 买到劣质板（引脚丝印错、USB 供电不足） | 中 | 一次买 3 块；先跑 LED 与 WiFi 冒烟测试再接线 |
| BLE 与 WiFi 并发不稳 | 中 | 分时策略：BLE 已连接时降低 WiFi 重连频率 |
| 内网穿透配置复杂 | 中 | 先用 Tailscale（零配置组网）兜底，再换 frp |
| TLS 内存不够 | 中 | 局域网用明文 + ACL；只对公网连接开 TLS |
| MQTT 掉线后不重订阅 | 高 | 重连回调里强制重订阅 + 重新发 LWT 设置 |
| 规则误触发（烟雾抖动疯狂开窗） | 高 | 规则必须有 `cooldown_s` |
| OTA 刷坏 | 中 | 双分区 + 回滚 + 启动计数 |
| 备考中断导致遗忘 | **高** | 每个模块文件顶部写清"职责 + 引脚 + 坑"；日志留"下次从哪继续" |
| 节点数超免费云额度 | 低（用自建 broker 就不会） | 见 docs/01 第 4.6 节 |

## 17. 交付与可靠性清单（来自 docs/08 市场调研）

> 这一章不是功能，是**保命条款**。市场调研里六起真实翻车案例，全部栽在这几条上。

### 17.1 交付时必须有（对应龙湖业主"连发票都没有"的教训）

| # | 交付物 | 内容 |
|---|---|---|
| 1 | **配置导出包** | `node_config.h` 备份、规则 JSON、设备清单、主题表，打包成 zip |
| 2 | **权限移交证明** | broker 账号密码、MQTT ACL 表、中枢管理员账号 —— 全部交给用户 |
| 3 | **拓扑图** | 谁连谁、broker 在哪、每台设备的 device_id 与位置 |
| 4 | **恢复手册** | 一页纸：中枢坏了怎么换、节点怎么重新配网、OTA 怎么回滚 |
| 5 | **固件版本清单** | 每个节点的 `fw` 版本与对应 bin 文件存档 |

### 17.2 中枢可替换（对应"网关单点故障"）

```
规则  → 存 JSON 文件，不在代码里
设备  → 靠 _discovery retain 自动发现，不手工录
状态  → retain 存在 broker，重启即恢复
结论  → 换一台中枢，装 broker + 拷规则文件，十分钟恢复
```

**验收**：故意把中枢断电 1 小时，换一台新设备顶上，全屋功能在 15 分钟内恢复。

### 17.3 误报抑制（对应"报警疲劳"）

| 机制 | 实现 |
|---|---|
| 冷却时间 | 每条规则必须有 `cooldown_s`，默认 60 |
| 二次确认 | 烟雾/跌倒类告警需连续 N 次（如 3 次/6 秒）才触发 |
| 分级响应 | 提醒 → 本地声光 → 推送 → （可选）重复呼叫 |
| 可静音 | 用户能静音某条规则而不删掉它 |

**验收**：连续制造 10 次瞬时抖动（吹一下烟雾传感器），只应产生 1 次有效告警。

### 17.4 永不设远程锁死（对应"商家远程锁网关"的恶性案例）

| 原则 | 说明 |
|---|---|
| 无后门 | 固件里不得有任何"远程停用"指令 |
| 本地优先恢复 | 任何禁用状态都能通过本地按键 + 断电重启解除 |
| 无到期失效 | 不做订阅到期即停机 |
| 源码可查 | 开源项目天然满足，但也要写进 README 承诺 |

### 17.5 面板可读性（对应"面板不刻字，老人直接懵"）

- [ ] 51 面板的每个键旁有**丝印或贴纸标注**（哪个键管哪个设备）
- [ ] LCD 显示用**中文 + 固定位置**，不滚动
- [ ] 断网时面板仍显示最后一次已知状态，并标注"离线"
- [ ] 不依赖手机才能操作任何核心功能

## 2026-11-07｜M0 架构修正（第二次）

**背景**：用户指出前版理解偏差 —— "所有电器连到一块 51"不现实，真正的意图是**每个电器一个 C3**，51 只做中控面板。

**修正内容**
1. **最小单元改为「一个电器 + 一块 C3」**，51 不再是主控
2. **51 从网关降级为面板节点**：51 + 一块 C3 当网卡，作为总线上的第四个同级订阅者，**不在数据路径上**
   - 理由四条：89C52 只有 1 个 UART（接不了 N 个节点）、256B RAM 存不下状态表、单点故障违背分布式初衷、C3 本可直连 WiFi 不必中转
3. **link 层可插拔**：`link_gpio`（纯节点，C3 直接驱动）/ `link_serial`（中控，C3 与 51 对话）。一份固件两种形态
4. **三种部署形态**取代原"两代架构"叙事：A 纯节点 → B 局域总线 → C 云端异地 / C+ 中控
5. **通信四层降级**：BLE → WiFi AP → 局域网 MQTT → 云端 MQTT，逐层兜底
6. **里程碑重排**：M1 改为"纯 C3 单节点原型"（原 M1 是 51 本地闭环）；51 四阶段转为**技能预科并行线**，不占主线工期
7. 节点芯片定为 **ESP32-C3 SuperMini**（WiFi + BLE5 双模 + OTA，约 12 元），ESP-01S 出局（无 BLE）

**关键洞察**
- 用户提出的两种形态，代码依赖顺序与直觉相反：**"只有 C3" 是地基，51 面板是上层**。所以必须先做纯节点。
- "分布式"在软件上的实现代价极低 —— 同一份 bin，只改 `node_config.h` 的 `DEVICE_ID` 与 `LINK_IMPL`。

**卡点**
- 待采购 ESP32-C3 ×2；决定 M2 的 broker 放在哪（常开 C3 / OpenWrt / 旧手机 / 树莓派）

## 2026-11-07｜M0 第三轮：拆解"总控"

**用户补充的两个设想**
1. 节点经 WiFi 传到 51（非物理连接），51 是总控，再由 51 连接云
2. 51 是家本地终端（平时手动用），出门时手机连云直接下达单个电器，不经过 51

**分析结论**
- 把"总控"拆成三层：**流量中枢 / 规则中枢 / 显示中枢**。用户要的是后两者，不是前者。
- 两个设想存在物理矛盾：设想 2 成立 ⟹ 节点自己能连云 ⟹ 设想 1 的"经 51 上云"变成多余。二者不能以同一链路共存。
- 唯一自洽解：**节点连一个 broker，51 连同一个 broker**。broker 位置决定"总控成色"，不影响节点代码。

**新增决策表（docs/01 第 4.6 节）**
| 布法 | broker 位置 | 51 挂机后果 |
|---|---|---|
| 甲 | 51 的 C3 上（broker + 云桥接） | 全屋失联 |
| **乙（采纳）** | 常开设备（旧手机/树莓派/OpenWrt） | 其他照常 |
| 丙 | 云端 | 无影响，断外网即瘫 |

选乙，保留将来把 broker 挪到 51 的 C3 上的可能（节点代码不用改）。

**重要结论**：该决策**不阻塞 M1**。节点固件只认"一个 broker 地址"，broker 放哪属部署问题。M1 立即可开工。

**下次从哪继续**
- 采购 ESP32-C3 ×3 → M1：C3 + 28BYJ-48 + BLE 直控

## 2026-11-07｜M0 定稿：51 = 显示主控，broker 另置

**用户确认的最终形态**
- 51 作为家里的**显示主控中心**：LCD 显示全屋、按键可直接控制、断网跑本地联动
- 手机既能通过云控制单个电器，也能操作 51 面板
- 疑问：电器是否要"既连云又连 51"？

**回答要点**
1. **不需要两条连接**。MQTT bridge 让家 broker 与云 broker 同步为一个逻辑网络：三个客户端各 1 条连接（都连家 broker），家 broker 用 1 条桥接上云。节点对云无感。
2. **broker 不放在 51 上**，四条理由：51 跑不了（真实是 C3 在跑，名不副实）；**烧程序必重启 ⟹ 调代码与全家在线互斥**（最要命）；单点故障；C3 上 broker+桥接+TLS 内存紧，易随机掉线。
3. broker 载体优先级：**OpenWrt 路由器（0 成本、本就 7×24）> 旧手机（自带 UPS，但有杀后台/电池鼓包坑）> 树莓派 > 专用 ESP32-S3 > 云 broker**。

**架构定稿（M0 收尾）**
```
窗帘C3 ─┐
灯  C3 ─┼→ 家broker(路由器/旧手机/派) ←bridge→ 云broker ← 手机4G
51 面板 ─┘
```
51 只订阅与发令，不转发；节点只连家 broker，不知道云在哪。

**下次从哪继续**
- 查路由器型号能否刷 OpenWrt（M2 用）
- 采购 ESP32-C3 ×3 → M1：C3 + 28BYJ-48 + BLE 直控（不需要 broker）

## 2026-11-07｜M0 收尾：项目拆分（51 移出主线）

**用户的核心洞察**
- 本地中枢（旧手机/树莓派）实质就是"本地云"，与巴法云同性质：只收发消息，不做判断
- 判断应该交给节点；中枢负责"发现温度过高就发命令开风扇/开窗"
- 由此推出：中枢可以同时兼任 broker 与规则引擎，**不再需要 51**
- 结论：把 51 拆出去做原来的文档项目，本项目专注"本地中枢 + C3 节点"

**采纳并执行的拆分**
| | 项目一 `51-SmartHome/` | 项目二 `SmartHome/`（本项目） |
|---|---|---|
| 目的 | 学习，把 51 与外设打熟 | 产品，能装进房子的分布式系统 |
| 是否依赖对方 | 否 | 否，51 面板降为可选扩展 |

- 新建 `51-SmartHome/`：README + 计划与验收 + 开发日志 + firmware 说明（含 4 条落地修正）
- `SmartHome/` 移除主线中的 51：README 定位改写、M5 改为"中枢规则编排"、docs/00 新增「项目边界」章节、docs/01 第 4 章标注为可选扩展

**补充的架构澄清（三层决策分工）**
- 层一 节点本地闭环：同节点内的联动，200ms，断网照常 → 例：本机温度→本机风扇
- 层二 中枢跨设备编排：需要全局状态 → 例：S01 烟雾 → C01 开窗
- 层三 云端只为出口：异地访问、推送

**关键论点**：用户说"判断由节点做"是对的，但**跨设备联动节点做不了**，因为节点不该知道别的节点存在。所以中枢存在的理由不是"做判断"，而是"持有全局状态"。判断归节点，协调归中枢，两者不是二选一。

- 米家不推广 Zigbee 了，传感器推荐 BLE。**电池设备用 WiFi 是不成立的**（2000mAh 只能撑几天）→ 写进 docs/06 第 16 节未来扩展的约束。
- MIoT-Spec 用 service/property 描述能力，App 只认属性不认型号 → 我们做简化版 capability 模型 + `_discovery` retain 自动发现，新增节点不改中枢代码。
- miIO 用 device ID 寻址而非 IP；早期固件在 hello 回复里明文吐 token 导致全屋可被同网段控制 → 教训：不自己发明加密，用 TLS + ACL。
- HA 的 automation 三段式（trigger/condition/action）直接作为规则引擎 JSON 结构，必须带 `cooldown_s` 防抖。

**给用户的两条建议（已在文档中体现）**

4. HA MQTT Discovery：config 主题 + 完整 payload（switch/light）、缩写表、availability 解决"幽灵设备"
5. BLE 配网：三种实现对比（Espressif protocomm / Zephyr / 自制）、五个特征表、四态状态机、MTU 517
6. 四套方案横向对比
7. **capability spec v1**（冻结）：四种能力（switch/cover/dimmer/sensor）、属性四件套、`_discovery` 完整报文、HA 兼容双发、指令语义五动词
8. 八条照做清单

**最有价值的五个实现细节**
1. **URN 命名**：`power` 是标准化的全球唯一名，不是厂商自起 → 任何 App 都认识。这是跨品牌互通的真正机制（不是"统一协议"，是"统一命名"）。
2. **MIoT 的服务化方法**：`get_properties`/`set_properties`/`action` 全设备通用，对比老 miIO 的 `set_bright` 每设备一套 → 方法名不需要为每个型号重定义。
3. **Matter 的刻度陷阱**：LevelControl 的 CurrentLevel 是 **0–254**（255 保留表示"上次非零值"）；温度用 int16 表示 **0.01℃**。原文原话是"把这些单位搞错是互操作测试里最常见的失败点"。
4. **HA Discovery 零代码接入**：设备往 `homeassistant/<type>/<id>/config` 发一条 retain JSON 就自动注册。我们抄这套 → M6 上位机白捡一大半。
5. **BLE 配网只要 4 个特征**：SSID/PASS/CONTROL/STATUS + MTU 517 + 四态状态机。比想象中简单得多。

**对项目的影响**
- `docs/06` 第 5 节标注 spec 以 docs/09 第 7 节为准（v1 冻结）
- 刻度约定按 Matter 的教训定死：温度 int16 单位 0.1℃；百分比 0–100 整数；布尔用 0/1 省字节
- 接入 HA 的唯一难点是 cover 状态字符串映射（open/closed/opening/closing ↔ pos 数字），需用 template 转换

5. AI 模块定位：M9 独立子项目，原则是"AI 是总线上的虚拟传感器，不是核心"
6. 变更记录（4 条，已标注需同步的旧文档）

**本轮三个最重要的技术判断**
1. **双连接有四个坑**：同一 broker 上 client_id 重复会互相踢下线（最阴）；状态必须双写；指令要带 ts+seq 去重；重连退避要加随机抖动错开。RAM 代价约 40KB（TLS），C3 可承受，但不能再加第三条。
2. **物理开关必须与继电器触点并联到负载**，不能只做 MCU 的输入信号。否则"手动"只是"通过 MCU 手动"，MCU 一死全废。这是整个项目最不能做错的一件事。
3. **AI 上云要算两笔账**：1080p 持续上传约 0.6–1.2 TB/月；建议"本地判断何时上传、云端判断上传后是什么"，降幅 99%。隐私上更稳的做法是**特征上云、原图不上云**。

**分期建议**：M2–M4 先单连接跑通，M7 再加第二连接。一次只引入一个新变量，否则调试时分不清是哪条链路出问题。

## 2026-11-07｜重要修正：开关接法推翻重做

**用户第二次追问"手动开灯、手机关灯怎么实现"，逼出了一个错误。**

### 错在哪

早期方案给的是「机械开关与继电器**并联**（+ 电流检测）」。
但并联是**"或"逻辑**：任一路闭合即通电 → 物理开关闭合着时，继电器断开也没用，电从开关那条路过去了。
**结果：手机永远关不掉一盏被手动打开的灯。** 而这正是用户最核心的诉求。

### 正确解法（方案 ③）

> **物理开关只"说话"，MCU 唯一"动手"。**

```
物理开关(SPDT 自锁) ──信号──→ MCU ──驱动──→ 继电器 ──→ 负载
                                 ↑
                          手机 / 云 / 终端

应急拨杆（平时断开）──────────────→ 负载   ← 仅 MCU 死机时手动合上
```

| 接法 | 手动开灯 | 手机关灯 | MCU 死机能开 |
|---|---|---|---|
| ① 串联 | ✅ | ✅ | ❌ |
| ② 并联 | ✅ | ❌ **关不掉** | ✅ |
| **③ 输入信号 + 独立应急拨杆** | ✅ | ✅ | ✅ |

### 四条关键细节
1. 物理开关用 **SPDT 自锁**（能读出"想开/想关"），瞬时按钮做不到
2. **上电时把继电器同步到开关位置**，否则开关在"通"位而继电器是断的，用户拨一下反而没反应
3. 应急拨杆必须**独立器件**，平时断开，不参与日常操作
4. **电流检测降级为可选**（只做执行确认，防触点粘连）—— 因为 MCU 已是唯一执行者，不需要靠检测去"猜"状态

### 一个印证
市面正规智能墙壁开关本质也是这个结构：面板按键 = MCU 输入，继电器 = 唯一执行者。
**我们不是创新，是回到正确做法**；唯一多做的就是加 3 块钱的应急拨杆，补上商用产品"MCU 死了就废"的通病。

- `docs/10` §4.2 重写（删掉错误的并联图）

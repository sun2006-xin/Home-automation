# 13 · 场景与联动设计

> 本文定义"回家/离家/睡眠"这类场景怎么编排，以及它和"自动化规则"的边界。
> 核心结论：**场景不是"发一串指令"，而是一次有进度、可取消、能回报的执行实例。**

---

## 0. 三个概念必须分清

混在一起是灾难的开始。参照涂鸦的做法，明确拆开：

| 概念 | 谁触发 | 生命期 | 例子 |
|---|---|---|---|
| **场景（scene）** | **人点一下** | 一次性，有开始与结束 | 回家、离家、睡眠 |
| **自动化（automation）** | **条件满足** | 持续监听，反复触发 | 温度 > 30 自动开风扇 |
| 快捷操作 | 人点单个设备 | 瞬时 | 开灯 |

**为什么必须分开**：
- 场景需要"进度、取消、部分失败"这套复杂状态机
- 自动化需要"去抖、冷却、触发条件"这套复杂判定
- 混成一个东西，两边都做不好

> 但它们**底层用同一个动作结构**，只是 `trigger` 不同（见第 9 节）。

## 1. 场景的数据结构

```json
{
  "id": "scene_home",
  "name": "回家",
  "icon": "home",
  "actions": [
    {"dev": "L01", "cmd": "set", "args": {"on": 1}, "at": 0},
    {"dev": "C01", "cmd": "set", "args": {"pos": 50}, "at": 0},
    {"dev": "F01", "cmd": "set", "args": {"on": 1}, "at": 0,
     "when": {"dev": "S01", "attr": "t", "op": ">", "val": 280}},
    {"dev": "H01", "cmd": "set", "args": {"on": 1}, "at": 0,
     "long": true, "eta_s": 1200, "note": "加热约 20 分钟"},
    {"dev": "L03", "cmd": "set", "args": {"on": 0}, "at": 5}
  ],
  "reentrant": false,
  "abort_on_fail": false,
  "notify_on_done": true
}
```

| 字段 | 含义 | 说明 |
|---|---|---|
| `at` | 相对场景开始的秒数 | 比 `delay` 直观，便于重排顺序 |
| `when` | 该动作的执行条件 | 条件不满足则跳过，不算失败 |
| `long` + `eta_s` | 长尾动作标记与预计耗时 | UI 用它画进度条 |
| `reentrant` | 是否允许重复触发 | false 时连点第二次被忽略 |
| `abort_on_fail` | 一个动作失败是否中止后续 | 默认 false（尽量做完） |
| `notify_on_done` | 完成是否推送 | — |

## 2. 执行实例（这是"不是一串指令"的关键）

场景被点下后，产生一个**执行实例**：

```json
{
  "run_id": "r_1730_01",
  "scene": "scene_home",
  "state": "running",
  "progress": 0.15,
  "done":   ["L01", "C01", "F01"],
  "pending":["H01", "L03"],
  "failed": [],
  "started": "2026-11-07T19:40:12+08:00"
}
```

| state | 含义 | UI 表现 |
|---|---|---|
| `pending` | 已创建，还没开始 | 按钮转圈 |
| `running` | 执行中 | 进度条 + "取消"按钮 |
| `done` | 全部完成 | 一次性提示后消失 |
| `cancelled` | 用户取消 | 提示"已取消，热水器已关闭" |
| `partial_fail` | 部分失败 | 列出失败设备 + "重试失败项" |

**必须能取消。** 场景：地铁上点了"回家"烧热水，结果临时改道去吃饭 → 点取消 → 热水器关掉，已开的灯保持（不会把你刚开的灯也关掉）。

## 3. 回家模式（完整设计）

| 顺序 | 动作 | 时间 | 条件 | 失败处理 |
|---|---|---|---|---|
| 1 | 玄关灯开 | 0s | — | 跳过 |
| 2 | 客厅灯开 | 0s | — | 跳过 |
| 3 | 客厅窗帘开到 50% | 0s | — | 跳过 |
| 4 | 空调开 | 0s | 室内温度 > 28℃ | 跳过 |
| 5 | **热水器开** | 0s | — | **单独提示** |
| 6 | 主卧灯关 | 5s | — | 跳过 |
| 7 | 推送"热水器加热中，约 20 分钟" | 0s | — | — |

**三个设计要点：**

1. **第 6 条为什么延时 5 秒**：全屋灯同时亮会刺眼，也让"回家"这件事失去了层次。
   5 秒后再关卧室灯，是一种"人已经在客厅了"的节奏感。
2. **第 4 条为什么带条件**：冬天开空调加热，夏天开制冷，春秋根本不用开。
   硬开空调是很多"智能"让人反感的原因。
3. **第 5 条单独提示**：因为它要跑 20 分钟，必须让用户知道"它在工作"，否则会以为没反应而重复点。

## 4. 离家模式

| 动作 | 说明 |
|---|---|
| 关闭全部可控设备 | **带排除清单**，见下 |
| 空调关 | — |
| 窗帘关 | — |
| 安防布防 | 人体感应进入告警模式（不再自动开灯） |
| 扫地机启动 | 可选 |
| 推送汇总 | "已关闭 7 台，保留 2 台（冰箱、路由器）" |

### 4.1 "全部关闭"的坑：广播会误伤

如果直接发 `sh/h01/broadcast {"cmd":"all_off"}`，**冰箱插座、路由器、摄像头也会被关**。
后果：冰箱化冻、全家断网、监控中断 —— 而且断网后你连"取消"都发不出去。

**三种解法对比：**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 甲 | 节点标记 `critical: true`，收到 all_off 时自己忽略 | 简单 | 行为分散在各节点，难排查 |
| 乙 | 广播带 `exclude: ["H02","..."]` | 一次通信 | 载荷变长，节点要解析列表 |
| **丙（推荐）** | **中枢遍历设备表，逐个下发，跳过 critical** | 可控、能统计、能重试 | 多条消息 |

**选丙**。因为只有它能回答"哪几台关了、哪台失败了"。广播只说"我喊过了"。

> 这也是 docs/12 里"离线态要如实显示"的同一条原则：
> **宁可告诉用户"1 台失败"，也不要假装全部成功。**

## 5. 睡眠模式

| 动作 | 说明 |
|---|---|
| 全屋灯关（除夜灯 L00） | 夜灯保留，起夜不摸黑 |
| 窗帘关 | — |
| 空调调到 26℃ 静音 | 不是关掉，是调柔 |
| 安防切"在家布防" | 人体感应不报警，只记录 |
| 推送"晚安，全屋已就绪" | — |

## 6. "提前烧热水"的三种实现

你提的这个需求，其实有三种触发方式，可以并存：

| 方式 | 触发 | 复杂度 | 建议 |
|---|---|---|---|
| **A 手动预启动** | 在外面点"准备回家" → 只跑预热动作 | 低 | **v1 就做** |
| **B 定时** | 每天 18:00 自动预热 | 低 | v1 就做 |
| C 地理围栏 | 离开公司 / 距家 3km 自动触发 | 中（定位 + 隐私授权） | v2 |

**关键：A 和 B 用的是同一套"预动作"**，只是触发器不同。
所以先把"预动作"抽象出来：

```json
{
  "id": "pre_heat_water",
  "name": "预备回家",
  "actions": [
    {"dev": "H01", "cmd": "set", "args": {"on": 1}, "at": 0,
     "long": true, "eta_s": 1200}
  ],
  "notify_on_done": true
}
```

然后"回家"场景可以直接复用它（`include: ["pre_heat_water"]`），定时任务也复用它。

## 7. 并发与冲突

| 情况 | 处理 |
|---|---|
| 连点两次"回家" | `reentrant: false` → 忽略第二次，按钮显示"执行中" |
| 回家执行中又点"离家" | **新场景优先**。取消回家的未执行动作（热水器关掉），已执行的保留 |
| 两个设备被两个场景同时控制 | 后执行者胜，但要在日志里记下两次 |
| 场景执行中用户手动改了某设备 | 不改场景的后续动作，但最终汇总里注明"L01 被手动修改" |

**原则：用户的直接操作永远高于场景的编排。** 场景是"帮你想好的建议"，不是"接管你的手"。

---

## 8. 失败处理

| 情况 | 处理 |
|---|---|
| 单个设备离线 | 跳过，记入 `failed`，最后汇总提示 |
| 指令超时（1s 无 state 回报） | 重试 1 次（间隔 500ms），仍失败则跳过 |
| 长尾动作失败 | 单独提示，不影响其他动作 |
| 全部失败 | 提示"检查网络或设备电源" |
| 部分失败 | 提供"重试失败项"按钮，只重跑 failed 里的动作 |

## 9. 与自动化共用同一套动作结构

场景和自动化**底层同构**，只差 `trigger`：

```json
// 场景：人点
{"trigger": {"type": "manual"}, "actions": [...]}

// 自动化：条件满足
{"trigger": {"type": "device", "dev": "S01", "attr": "smoke", "op": ">=", "val": 1},
 "actions": [{"dev": "C01", "cmd": "set", "args": {"pos": 100}, "at": 0}],
 "cooldown_s": 60}

// 自动化：定时
{"trigger": {"type": "schedule", "cron": "0 18 * * *"},
 "actions": [{"dev": "H01", "cmd": "set", "args": {"on": 1}, "at": 0}]}
```

**好处**：规则编辑器只做一套表单，执行引擎只写一个调度器。
新增"地理围栏触发"只是加一种 `trigger` 类型，动作部分完全不动。

> 结构已定稿（见 docs/10）。本文定义**做哪些东西、每个东西长什么样、具备什么功能**。
> 不含代码，只定产品。

## 0. 第一原则：状态只认实测，不认命令

这是整个产品的宪法。所有功能讨论都要回到它。

| 谁 | 在状态这件事上的角色 |
|---|---|
| **节点（电器）** | **唯一真源**。它报什么就是什么 |
| Broker | 状态的中转与暂存（retain） |
| 终端 / 手机 / 云端 | **纯订阅者**，各自不维护独立状态 |

### 三条铁律

1. **界面不许"点一下就变"**。
   点按钮 → 发指令 → 进入 `pending`（转圈/半透明）→ 等节点回 `state` 才确认。
   超时 1 秒没回 → 回滚 + 提示"设备未响应"。
2. **物理操作最高优先级**。
   人在现场按了开关，那就是事实。App 的待执行指令立即作废，界面跟着物理状态走。
3. **冲突按序号定胜负**。
   每条指令带 `seq`（自增），节点只认比当前更大的 `seq`，小的丢弃。防止旧指令"穿越"。

> 反面案例：很多 DIY 项目点一下界面立刻变色，但继电器其实没动。
> 用户以为开了，回家发现是黑的。**这就是"两套系统"。**

## 1. 家电清单

### 1.1 第一梯队（MVP，必须做）

| 家电 | 能力类型 | 为什么先做 | 难度 | 估价 |
|---|---|---|---|---|
| **智能灯**（1 路） | `switch` | 最直观、演示效果最好、无机械风险 | ★ | ~15 元 |
| **智能插座** | `switch` | 通用，可接任何负载（风扇/台灯/加湿器） | ★ | ~20 元 |
| **智能窗帘** | `cover` | 有电机，练"百分比定位 + 限位" | ★★★ | ~10 元 |
| **温湿度传感器** | `sensor` | 数据源，规则引擎的输入 | ★ | ~8 元 |

**这一组覆盖了全部 4 种能力类型**，做完就等于把协议跑全了。

### 1.2 第二梯队（体验完整）

| 家电 | 能力 | 说明 |
|---|---|---|
| 人体感应 | `sensor` | 回家自动开灯 / 无人延时关灯 |
| 烟雾 / 燃气 | `sensor` | **安全类**，逻辑要 fail-safe |
| 墙面智能面板 | 输入设备 | 替代或并列物理开关 |
| 红外万能遥控 | 特殊 | 控空调/电视这类"非智能"家电 |
| 门磁 / 窗磁 | `sensor` | 开窗自动关空调 |

### 1.3 第三梯队（进阶）

| 家电 | 说明 |
|---|---|
| 智能门锁 | **安全边界，见 1.4** |
| 摄像头 + AI | 独立模块 M9 |
| 环境控制（加湿/净化） | 其实只是插座 + 红外，不用单独做 |

### 1.4 门锁：必须先划安全边界

**开锁失败的后果不是"体验差"，是"人进不了家"或"财物损失"。** 所以单独定规矩：

| 阶段 | 做什么 | 要求 |
|---|---|---|
| **v1** | **不做真门锁**。用舵机/电磁锁做抽屉、柜子级别演示 | 验证"鉴权 → 开锁 → 状态回报 → 留痕"全链路 |
| v2 | 若上真门 | 必须同时满足下面五条 |

上真门的五条硬要求：

1. **断电 = 开**（fail-safe）。从室内出去永远不依赖电力。
2. **机械钥匙保留**，且不是摆设（能真开）。
3. **本地鉴权优先**：断网也能开，不依赖云端。
4. **不做"纯云端开锁"**。云只能发"请求"，实际开锁决策在本地。
5. **开锁记录本地留痕**，云端只做同步展示。

> 参照 docs/08：龙湖业主半年进不了自己家的门（智能系统全瘫）。
> 门锁这类设备，"能不能开"比"好不好用"重要一百倍。

## 2. 本地终端

### 2.1 三件套（已定稿）

| 角色 | 硬件 | 成本 | 定位 |
|---|---|---|---|
| **主终端** | **闲置旧手机**（壁挂 + 全屏浏览器加载 PWA） | **0 元** | 负责"看"与触摸控制。屏幕质量与触摸手感远胜同价位开发板 |
| **物理按键条** | 51（普中A2）+ LCD1602 + 4 按键 | **0 元**（已有） | 负责"按"与兜底。**正好是项目一第四阶段的产物** |
| 备选 | ESP32-S3 + 2.8–4 寸触摸屏 | ~150–250 元 | 旧手机不可用时的替代方案 |

**为什么是两件而不是一件**：旧手机有"看"，没有"按"。
它没有物理按键 —— 湿手按不准、老人看不清、碎屏就全废，而报警静音这类动作需要盲操。
所以一个负责好看，一个负责可靠。

> 旧手机的三个坑（电池鼓包 / 杀后台 / OLED 烧屏）与解法，见 `docs/12-界面设计规范.md` 第 4.3 节。
> 其中"用智能插座给终端控电（充到 80% 断）"既是安全措施，也是本项目第一个真实用例。

### 2.2 触摸屏还是按钮屏？—— 答案是都要

| 维度 | 触摸屏 | 物理按键 |
|---|---|---|
| 信息密度 | 高 | 低 |
| 盲操（不看就能按） | ❌ 差 | ✅ 好 |
| 老人 / 湿手 / 戴手套 | ❌ 差 | ✅ 好 |
| 成本 | 高 | 低 |
| 可靠性 | 中（碎屏、贴膜、沾水） | 高 |
| 适合干的事 | **看** | **按** |

**结论：屏负责"看"，键负责"按"。**

- 触摸屏：显示设备卡片、当前状态、告警、时间
- 4 个物理按键，功能**固定不变**：
  - 键 1：全屋关灯
  - 键 2：回家模式
  - 键 3：离家模式
  - 键 4：报警静音

> 依据 docs/08 的教训：\"面板装得漂亮但没刻字，入住后哪个键开客厅灯全靠记，老人直接懵。\"
> 所以按键**必须丝印或贴标**，且功能不能变来变去。

### 2.3 终端功能清单

| 分类 | 功能 |
|---|---|
| **显示** | 每个设备的状态卡片（在线/离线/当前值）；时间；网络状态；告警横幅 |
| **控制** | 4 个物理键（固定）；触摸屏点选单个设备（v2） |
| **场景** | 回家 / 离家 / 睡眠 / 全关 |
| **告警** | 本地声光 + 屏上弹出 + **必须手动确认**才消失 |
| **断网** | 显示最后一次已知状态，并标注"离线"；物理键仍可控制 |
| **设置** | 设备列表、屏幕亮度、音量、重新配网 |

**一个容易漏的点**：终端要能显示"这台设备是被谁操作的"。
比如日志里看到"客厅灯 · 由墙面开关打开 · 19:42"，用户才不会困惑"我没开啊"。

## 3. 云端（先在本地电脑跑）

### 3.1 你的判断是对的

> "云端本质就是把我们本地电脑运行的放在服务器"

完全正确。**开发阶段就在自己电脑上跑，一个字节都不用改就能搬家。**
只是把"局域网地址"换成"公网地址 + 证书"，别的一模一样。

### 3.2 本地电脑上跑什么

```
一台电脑上跑三件东西：
1. MQTT Broker        （mosquitto）
2. 规则引擎           （Home Assistant / Node-RED / 自写）
3. Web 服务           （界面）
```

### 3.3 云端界面功能清单

| 模块 | 功能 | 优先级 |
|---|---|---|
| **仪表盘** | 设备卡片（状态 + 快捷开关）；在线数；今日告警数 | P0 |
| **设备详情** | 实时值、历史曲线、重命名、分组、所属房间 | P0 |
| **场景编辑** | 触发 / 条件 / 动作三段式（对应 docs/09 的规则 JSON） | P1 |
| **告警中心** | 列表、确认、静音、按时间筛选、导出 | P1 |
| **操作日志** | 消息流水，含 `src` 字段（谁在何时用什么方式操作的） | P1 |
| **设备管理** | 节点发现（`_discovery`）、固件版本、OTA 推送 | P2 |
| **用户与权限** | 家庭分组、成员权限、访问令牌 | P2 |

### 3.4 技术选型建议

| 阶段 | 用什么 | 理由 |
|---|---|---|
| 第 1 周 | **Home Assistant** | 半天就能看到所有设备、曲线、自动化，先验证数据对不对 |
| 第 2–3 周 | **Node-RED**（如需复杂逻辑） | 拖拽画流程，规则调试比写代码快 |
| 之后 | **自写 Web**（PyQt5 或网页） | 想要定制界面时再写，前面两个用来对照 |

> 不要一上来就自写界面。先让 HA 跑通，你会得到一份"正确的参照物"。

## 4. 手机

### 4.1 不做原生 App

| 方案 | 开发成本 | 维护 | 建议 |
|---|---|---|---|
| iOS + Android 原生 | 高（两套代码） | 高（审核、签名） | ❌ |
| 微信小程序 | 中（要企业认证才能用 WebSocket） | 中 | 备选 |
| **PWA / 响应式网页** | **低（一套代码）** | **低** | ✅ **首选** |

**PWA 的好处**：手机浏览器打开 → "添加到主屏幕" → 有图标、全屏、能收推送，用起来和 App 差不多。

### 4.2 手机功能清单

| 模块 | 功能 | 优先级 |
|---|---|---|
| 设备卡片 | 一格一设备，显示状态 + 开关/滑块 | P0 |
| 房间分组 | 按房间切换 | P1 |
| 场景 | 一键回家/离家/睡眠 | P1 |
| 告警推送 | 浏览器推送 / 企业微信 / 邮件 | P1 |
| 状态实时性 | WebSocket 长连，物理操作 1 秒内反映到手机 | **P0** |
| 摄像头 | M9 之后再接 | P3 |

### 4.3 手机端必须处理的三个细节

1. **离线态**：手机不在同一网络且云端不可达 → 明确显示"离线"，所有按钮置灰。**不要假装能点。**
2. **弱网**：指令发出去没回应 → 显示"发送中"，1 秒后超时提示，不要把按钮变成"已开"。
3. **前后台切换**：从后台回来要**主动拉一次全量状态**（retain 主题），不能信任离开时的旧界面。

## 5. 物理开关 + 继电器 + MCU：接法（已修正）

> ⚠️ **本节的早期版本给错了方案**（当时写的是"并联 + 电流检测"）。
> 并联在"手机关灯"这个需求上直接失效，已推翻重写。

### 5.1 三种接法对比

| 接法 | 结构 | 手动开灯 | **手机关灯** | MCU 死机能开 |
|---|---|---|---|---|
| ① 串联 | 开关 → 继电器 → 负载 | ✅ | ✅ | ❌ |
| ② 并联 | 开关 ‖ 继电器触点 | ✅ | ❌ **关不掉** | ✅ |
| **③ 输入信号 + 独立应急拨杆** | 开关 → MCU → 继电器 → 负载 | ✅ | ✅ | ✅ |

**② 是很多人的第一反应，但它是错的：**
并联是"或"逻辑，任一路闭合即通电。物理开关闭合时，继电器断开也没用 —— 电从开关那条路过去了。**所以手机永远关不掉一盏被手动打开的灯。**

**这个需求一旦确认，结论就是唯一解：**

> 物理开关**不能直接通断负载**，它只能"说话"（给 MCU 位置信号）。
> **MCU 必须是唯一的执行者** —— 这样它才知道一切，状态天然准确。

### 5.2 最终接线：日常按钮 + 三档选择器（用户方案，已采纳）

**两层开关，各管一件事：**

```
日常按钮（接 MCU 输入）──→ MCU ──驱动──→ 继电器 ──→ 负载 ──→ 零线
                              ↑
                       手机 / 云 / 终端

火线 ── 三档选择器 ─┬─ ① 自动    → 经继电器（由 MCU 控）
                    ├─ ② 强制开  → 直通负载
                    └─ ③ 强制关  → 断路
```

| 档位 | 谁在控制 | 灯 | 远程控制 | MCU 上报 |
|---|---|---|---|---|
| **① 自动** | MCU（继电器） | 由 MCU 决定 | ✅ 可用 | `mode:"auto"` |
| **② 强制开** | 人手（直通） | 常亮 | ❌ 禁用 | `mode:"manual_on", on:1` |
| **③ 强制关** | 人手（断路） | 常灭 | ❌ 禁用 | `mode:"manual_off", on:0` |

**为什么这比"一个应急拨杆"更好：**

| 对比 | 单应急拨杆 | 三档选择器 |
|---|---|---|
| MCU 死机能开灯 | ✅ | ✅ |
| MCU 死机能**彻底断电** | ❌ 做不到 | ✅ ③ 档 |
| 模式是否明确 | 含糊（开/关？） | ✅ 自动/强开/强关，一看就懂 |
| 检修时是否安全 | 一般 | ✅ 能锁死在断开状态 |

> 工业上这就是 **AUTO / OFF / MANUAL 转换开关**，设备面板上的标准配置。
> 我们只是把它用到了家里的灯上。

**关键增益：档位要能回读给 MCU**

用 2 个 GPIO（或 1 个 ADC 读分压）把当前档位告诉 MCU。这样才能：

```
MCU 知道自己在 ② 档 → 上报 mode:"manual_on"
                    → 手机界面显示"手动模式"，远程按钮置灰
                    → 用户不会点了半天没反应还以为坏了
```

**不读档位的后果**：界面一直显示"可控"，用户点远程没反应 —— 又变成"两套系统"。

### 5.3 三种模式之外的第四个保险：电流检测

无论在哪一档，都在负载侧加一路电流检测（光耦 PC817，约 1 元）。

| 它能发现什么 | 为什么重要 |
|---|---|
| 继电器触点粘连（命令断，但仍有电流） | 这是继电器最常见的失效方式，光看状态看不出来 |
| 灯泡坏了 / 负载断线 | 界面显示"已开"但实际不亮 |
| 强制开档但负载没电 | 用户以为开了，其实没通 |

**一句话：开关位置是"意图"，电流检测是"事实"。两者都要有。**

### 5.4 关键细节

| 项 | 要求 | 原因 |
|---|---|---|
| 日常按钮类型 | 自锁或点动皆可，接 MCU 输入 | 它只是"表达意图"，不承担通断 |
| 三档开关类型 | **2P3T 旋转开关**（两刀三档） | 一刀选通路，一刀回读档位给 MCU |
| 带载切换 | 尽量在灯灭时切换档位 | 带载切换有电弧；12V 影响小，220V 必须选带灭弧的开关 |
| 切回自动的时序 | MCU 在进入 ① 档时，先把继电器同步到按钮/上次状态 | 否则从 ② 切回 ①，继电器是断的，灯会突然灭 |
| 触点容量 | 按负载电流选，留 1.5 倍余量 | 感性负载启动电流大 |
| **刻字** | 必须标 **自动 / 强开 / 强关**，不要只写 ①②③ | 用户记不住数字含义 |
| 断电行为 | 明确：断电后继电器全断，灯灭 | 若要"断电保持"需双稳态继电器（复杂度上一档） |

### 5.5 为什么商用智能开关没做这个

市面上正规智能墙壁开关，本质是"**面板按键 = MCU 输入 + 继电器 = 唯一执行者**"。
你按面板那一刻，其实是 MCU 在动作，不是机械触点直接通断。

**但它们几乎都没有三档选择器** —— MCU 死了就彻底失控，这是它们的通病（也是投诉高发点）。

我们加一个 10 块钱的 2P3T 旋转开关，补上这个洞：
- ① 平时用，享受智能化
- ② 检修灯线时强制通电
- ③ 出远门时彻底断电

**成本 10 块，换来"永远不会被智能锁死"这个保证。**

### 5.6 安全注意

| 项 | 要求 |
|---|---|
| 强电隔离 | 继电器模块要带光耦隔离；调试时不要用手碰强电侧 |
| 零线 | 智能开关必须有零线（单火线会闪烁、兼容差，docs/08 有真实案例） |
| 负载类型 | 感性负载（电机、风扇）要加续流/RC 吸收 |
| 保险丝 | 每个受控回路加保险，别指望继电器自己扛 |
| 认证 | 自用可接受，但**不要做成插到别人家墙上卖的产品**（涉及 3C 认证） |

## 6. 一次操作的完整数据流

| 步 | 谁 | 做什么 |
|---|---|---|
| ① | 物理开关 | 用户按下，强电闭合 |
| ② | 节点 MCU | 200ms 内采样到电流 → 上报 `state{on:1, src:"wall"}` |
| ③ | Broker | retain 最新状态 + 广播给所有订阅者 |
| ④ | 手机 / 终端 / 云端 | 界面刷新为"已开" |
| ⑤ | 手机 | 用户点"关" → 发 `cmd{on:0, seq:12}` → 进入 pending |
| ⑥ | Broker → 节点 | 转发指令 |
| ⑦ | 节点 | 检查 seq → 断开继电器 → 采样确认无电流 |
| ⑧ | 节点 → 全体 | 上报 `state{on:0, src:"app", seq:12}` → 手机确认 |

**任何一环都不维护独立状态**，所以永远不会出现"手机显示开、实际是关"。

## 7. MVP 定义（第一版能跑起来的最小集）

| 优先级 | 内容 | 完成标志 |
|---|---|---|
| **P0** | 1 个灯节点 + 1 个窗帘节点 | 两种能力都能被控 |
| **P0** | 本地电脑 broker + 网页仪表盘 | 电脑上能看到两个设备 |
| **P0** | 物理开关 + 电流检测 | 手动开灯，网页同步显示 |

| P1 | 51 终端 v1 | LCD 显示状态 + 按键控制 |
| P2 | 场景、告警中心、历史曲线 | — |

## 8. 六项决策落定（2026-11-07）

| # | 决策 | 影响 |
|---|---|---|
| 1 | **终端用旧手机**（+ 51 做物理按键条） | 成本 0；要处理电池鼓包与杀后台；51 面板定位改为"按键条" |
| 2 | **灯只做开关**，不做调光 | 省掉 PWM + 可控硅/恒流驱动一整档复杂度；协议仍预留 `dimmer` 能力，以后能加 |
| 3 | **窗帘做百分比定位** | 需要限位开关或计时校准 + 断电位置记忆；比三态复杂，但能力强得多（可"开一半"） |
| 4 | **门锁做** | 走模拟路线（12V 电磁锁），必须遵守下面 8.1 的五条 |
| 5 | **云端界面自写** | 参考 `docs/12-界面设计规范.md`；先用 Home Assistant 当参照物，再自写 |
| 6 | **全部 12V 直流模拟，不碰 220V 强电** | 安全；方案 C 的并联+电流检测逻辑完全一样，只是电压不同 |

### 8.1 门锁（模拟版）的五条纪律

| # | 要求 | 说明 |
|---|---|---|
| 1 | 用 **fail-safe 型电磁锁**（断电即开） | 保证断电时人能从里面出来 |
| 2 | 保留**机械应急开锁** | 一个手动拨杆即可，模拟也要有 |
| 3 | **本地鉴权优先** | 断网也能开；云端只能"请求"，决策在本地 |
| 4 | **不做纯云端开锁** | 云端下发只能是 request，节点自己判断 |
| 5 | **每次开锁本地留痕** | 时间 + 来源（按键/手机/卡片），并同步到云端 |

> 虽然是模拟，但把这五条做对，将来换真锁时逻辑不用重写。
> 反过来，如果模拟阶段就"云端一点就开"，将来上真门必然出事。

## 9. 模拟方案：每个家电用 12V 怎么搭

全部走 12V 直流，**接线逻辑与 220V 完全一致**，只是电压安全。

| 家电 | 用什么模拟 | 能力 | 说明 |
|---|---|---|---|
| 智能灯 | 12V LED 灯带/灯泡 + 继电器 | `switch` | 最直观，亮起来就有成就感 |
| 智能插座 | 12V 输出口 + 继电器 | `switch` | 可插风扇、加湿器 |
| 智能窗帘 | 28BYJ-48 步进 + ULN2003 | `cover` | 步进本身 5–12V，天生适合模拟。百分比靠步数换算 + 限位开关校准 |
| 智能门锁 | **12V 电磁锁（断电即开型）** + 继电器 | `switch` + 鉴权 | 见 8.1 |
| 温湿度 | DHT22 或 DS18B20 | `sensor` | 单总线/单线，接线最简 |
| 烟雾 | MQ-2 模块（**用 DO 数字输出**） | `sensor` | 不用 ADC，模块自带比较器可调阈值 |
| 人体感应 | HC-SR501 | `sensor` | 高电平输出，2m 内可靠 |
| 门磁 | 干簧管 + 磁铁 | `sensor` | 最便宜的开关量 |
| 电流检测 | **光耦 PC817 + 分压电阻**（只判有无电）/ **INA219**（I2C 读数值） | 辅助 | 方案 C 的关键件。⚠️ **不要用 SCT-013** —— 它是交流互感器，直流回路读数恒为 0 |

### 9.1 一个必须提前准备的电源方案

12V 模拟会同时带：步进电机（启动瞬间电流大）、继电器（线圈反向电动势）、LED、传感器。

| 要求 | 做法 |
|---|---|
| 电源容量 | 12V / 3A 以上（步进 + 多路继电器同时动作） |
| 电机独立供电 | 步进用单独一路 12V，或加大电容（1000µF）吸收启动冲击 |
| 共地单点 | 所有模块 GND 汇到一个点，避免地环路导致复位 |
| 继电器续流 | 模块自带续流二极管；裸继电器要外并 1N4148 |
| 保险 | 每路受控负载串一个自恢复保险丝（如 500mA） |

> 这一条不是理论：docs/02 里"电机启动瞬间导致 51 复位"就是这个原因。
> 12V 模拟一样会复现，别以为低压就不会有事。

### 9.2 模拟保真度：能证明什么，不能证明什么

**项目定位（写死，防止自欺）**：
> 本项目是**最大程度模拟**，目的是**快速验证想法与架构**，不是做成可上市的产品。
> 真正的产品化（安规、EMC、可靠性、认证、量产）是商家的事 —— 那是另一条成本曲线。
> 我们的优势是**快**：几天内把一套架构跑通、证伪、再迭代。

| 维度 | 模拟保真度 | 结论能否外推 |
|---|---|---|
| 拓扑与接线逻辑（并联旁路、保险位置） | **高**，与 220V 完全一致 | ✅ 能 |
| 通信协议与状态同步 | **高**，与电压无关 | ✅ 能 |
| 场景编排与时序 | **高**，完全一致 | ✅ 能 |
| 指令冲突与去重逻辑 | **高**，完全一致 | ✅ 能 |
| 故障模式（断网、断电、继电器卡死、节点死机） | 中，可模拟大部分 | ⚠️ 部分能 |
| 负载特性（浪涌、感性、功率因数） | 低，LED 灯带远小于真实灯具 | ❌ 不能 |
| 发热与线径选型 | 低，12V/1A 与 220V/5A 完全不同 | ❌ 不能 |
| 电气安全（漏电、电弧、绝缘） | 无 | ❌ 不能 |
| EMC / 抗干扰 | 低，小电流干扰小得多 | ❌ 不能 |
| 安规认证（3C） | 无 | ❌ 不能 |

**一句话**：
> 能证明「**架构和逻辑是对的**」，不能证明「**这个产品能卖**」。

**所以对外描述项目时，措辞要准确**：
- ✅ "验证了分布式节点架构与状态同步机制"
- ✅ "设计了带物理旁路的双通道控制方案，并用 12V 等效电路验证了逻辑"
- ❌ "做了一套智能家居系统"（容易被理解成可用产品）
- ❌ "实现了智能开关"（没做安规，不能称产品）

### 9.3 用电池模拟"火线有电"的三个讲究

思路对，但细节要把握：

| # | 讲究 | 原因 |
|---|---|---|
| 1 | **日常供电用 12V 适配器，不要用电池** | 电池电压随电量下降（12.6V→10.5V），继电器会吸合不稳、步进电机会丢步 |
| 2 | **电池只用来做"断电测试"** | 拔掉适配器 = 模拟市电断电，这正是"故障矩阵"要验证的场景 |
| 3 | **要测"切换瞬间"必须加二极管隔离** | 适配器与电池直接并联会互相倒灌；用二极管（或理想二极管模块）做"或"逻辑，才是真的 UPS 切换 |

**最有价值的一个测试**（也是整个项目最难造假的验证）：
> 把终端和云全断掉，只靠物理开关，看家里还能不能正常用。
> 这就是故障矩阵的最后一行 —— 它没法用软件"假装"通过，只能靠这套 12V 电路真的验证。

# 01 · 架构设计

> ⚠️ **本文已被 `docs/10-系统结构定稿.md` 部分更新。**
> 差异点：电器从"只连本地 broker"改为"**同时连本地 broker 与云 broker**"；新增物理开关旁路为强制项；云端新增 AI 推理职责。
> 冲突时以 docs/10 为准，本文保留作为推导过程记录。

## 1. 一句话

**最小单元不是"一块板子"，而是"一个电器 + 一块 C3"。** 51 退居二线，变成墙上的中控面板，可选。

---

## 2. 原子单元：节点

```
节点 = 一个受控电器（窗帘电机 / 灯 / 风扇 / 传感器组）+ 一块 ESP32-C3
```

C3 是每个电器的"网卡 + 边缘大脑"：自带 WiFi STA、WiFi AP、BLE 5.0，能跑 MQTT、能 OTA、有足够 RAM 和 GPIO。

**关键设计：C3 固件的 `link` 层可插拔。**

```c
/* link/link.h —— 两种实现，接口一致 */
typedef struct {
    void          (*init)(void);
    void          (*apply)(const char *cmd, const char *arg);  /* 执行指令 */
    unsigned char (*read_state)(char *buf, unsigned char max); /* 回报状态 */
} link_t;

extern const link_t link_gpio;    /* 纯节点：C3 直接驱动继电器/电机/传感器 */
extern const link_t link_serial;  /* 中控节点：C3 通过 UART 与 51 对话 */
```

> **这一个抽象，把"两种形态"变成了"一份固件 + 两种 link 实现"。**
> 不插 51 → `link_gpio`；插上 51 → `link_serial`。上层 net / cloud 代码一行不改。

---

## 3. 三种部署形态（同一套节点固件）

| 形态 | 组成 | 通信路径 | 典型场景 | 达成里程碑 |
|---|---|---|---|---|
| **A 纯节点** | 电器 + C3 | 手机 ↔ C3（BLE 直连 / WiFi AP 直连 / 同网 MQTT） | 单间、宿舍、出租屋，无常开服务器 | M1 |
| **B 局域总线** | N×C3 + 本地 broker | 手机 ↔ broker ↔ 节点 | 一个家，低延迟，断外网可用 | M3 |
| **C 云端异地** | N×C3 + 云 broker + 穿透 | 手机(4G) ↔ 云 ↔ 节点 | 异地、多宅、远程看家 | M4 |
| **C+ 中控形态** | 上述任一 + 51 面板 | 51 作为同级订阅者接入总线 | 墙上有个看得见摸得着的面板 | M5 |

形态之间**不是四套系统**，是同一批节点在不同组网深度下的表现。

## 4. 51 的角色：可选扩展，非必需

> ⚠️ 本章为**可选扩展**。51 仅作终端按键条（`firmware/node51/`），不参与节点主控，也不是独立项目。
> 本项目的主线（M1–M4、M6–M7）**完全不需要 51**。下面保留本章，仅供将来想做一块墙上物理面板时参考。

### 4.1 正确形态

```
[窗帘] C3 ─┐
[灯]   C3 ─┼──→ MQTT Broker ←── 手机 / 上位机
[风扇] C3 ─┤
[51+C3] ───┘        ← 51 是第四个订阅者，不是路由器
```

51 通过一块 **C3 当网卡**（UART 行协议连接），由这块 C3 代它订阅/发布。51 自己永远不懂 WiFi、MQTT、TCP。

```
51 ──UART 行协议──→ C3 ──MQTT──→ Broker
   L01;ST=1              sh/h01/panel/state
   LCD;T=25.3
```

### 4.2 为什么 51 不能当网关（四条硬理由）

| # | 理由 | 后果 |
|---|---|---|
| 1 | 89C52 **只有 1 个 UART** | 最多接 1 个模块，物理上接不了 N 个 C3 |
| 2 | **256B RAM** | 存不下多节点状态表、MQTT 报文缓冲 |
| 3 | **单点故障** | 51 死机 → 全屋失联，恰好违背了"分布式"的初衷 |
| 4 | **C3 本身就能直连 WiFi** | 绕道 51 等于直连可用却硬加中转，延迟翻倍、故障面翻倍 |

> 一句话：**分布式系统的中心不应该是一个必须常开才能工作的单片机。**

### 4.3 那 51 到底还有什么用

| 价值 | 说明 |
|---|---|
| 断网可用的物理面板 | 老人、客人、手机没电时都能用，这是真实需求不是摆设 |
| 本地联动快 | 51 本地判断 200ms 级，走云往返 1–3s |
| 屏幕与实体按键 | LCD1602 显示全屋状态，比掏手机快 |
| 学习主线 | 51 打好 GPIO/UART/单总线/ADC/电机基础，是嵌入式基本功 |
| 项目"的脸" | 视频里一块亮着的面板，比一堆屏幕截图有说服力 |

### 4.4 "总控"这个词的三层含义

同一个词，在架构里可以指三件完全不同的事。把它们拆开，争论就消失了：

| 位置 | 51 具体做什么 | 数据是否流经 51 | 51 挂机会怎样 |
|---|---|---|---|
| 流量中枢 | 当 MQTT broker / 中继 / 网关 | **是** | 全屋失联 |
| **规则中枢** | 订阅全部 state，跑场景规则，下发 cmd | **否** | 其他节点照常，只是不再自动联动 |
| 显示中枢 | LCD 显示 + 实体按键 | 否 | 只是看不到状态 |

> **结论：「总控」的实质是决策权集中，不是数据必须流经。这两件事在架构上可以完全分开。**
>
> 我们需要的 51 是「规则中枢 + 显示中枢」，不需要「流量中枢」。

### 4.5 两个设想的物理矛盾（必须正视）

| 设想 | 隐含前提 | 推出的结论 |
|---|---|---|
| 节点经 WiFi 传 51，51 再上云 | 节点只与 51 通信 | 远程必须经过 51，云没有直达节点的路 |
| 出门手机连云，直接下达单个电器 | 节点自己能连上云 | "经 51 上云"这一跳变成可选、甚至多余 |

**两者不能以同一条链路同时成立。** 唯一的自洽解：**节点只连一个 broker，51 也连同一个 broker。**
broker 放在哪，决定"51 总控"的成色；但节点代码完全不受影响。

### 4.6 broker 放哪（决定"51 总控"像不像）

| 布法 | broker 位置 | 51 的角色 | 远程路径 | 51 挂机后果 |
|---|---|---|---|---|
| 甲 | 51 的那块 C3 上（跑轻量 broker + 云桥接） | 名副其实的网关 | 云 → 桥接 → 51 → 节点 | **全屋失联** |
| **乙（推荐）** | 常开设备（旧手机 / 树莓派 / OpenWrt 路由器） | 规则 + 显示中枢 | 云 → 穿透 → 家 broker → 节点 | 其他照常 |
| 丙 | 云端 | 规则 + 显示中枢 | 云直连节点 | 无影响，但断外网即瘫 |

**选乙。** 它同时满足"51 是家里说了算的那台机器"（体验上）与"51 不会成为单点"（工程上）。
甲的差别只是 broker 搬了个位置，代价却是全屋依赖 51 —— 而这恰好是我们最初要避免的。
若将来确实想要"家里一切围着 51 转"的观感，把乙的 broker 挪到 51 的 C3 上即可，节点代码一行不改。

### 4.7 这个决策不阻塞 M1

无论选甲乙丙，**节点固件代码完全一样**：连一个 broker 地址，收发主题。
broker 放哪是**部署问题**，不是编码问题。所以 M1 现在就能开工，M2 再定。

### 4.8 桥接：为什么电器不需要连两个地方

常见误解：「电器既要连云、又要连 51，所以要维护两条连接」。

**不需要。** MQTT 的 **bridge（桥接）** 机制让两台 broker 自动同步主题，对外表现为同一个逻辑网络：

```
窗帘 C3 ─┐
灯   C3 ─┼→ 家里 broker ←─bridge─→ 云 broker ←─ 手机 4G
51 面板 ─┘   （1 条连接）            （公网可达）
```

- 三个客户端各自只维持 **1 条**连接，都连家里那台 broker
- 家里 broker 用 **1 条**桥接连到云 broker
- 手机异地连云端，指令经桥接自动回流到家里的 broker，**节点完全无感**

**收益**：
- 节点不需要知道云在哪，也不需要 Wi-Fi 之外的第二套连接逻辑
- 云侧不需要直连任何设备，也就没有端口映射 / DDNS / 设备公网暴露的问题
- 家里断外网时，本地这条总线照常工作，只是桥接那条断了

> 一句话：**是"一台设备干两份活"，不是"每个电器两条连接"。**

### 4.9 为什么 broker 不放在 51 上

| # | 理由 | 说明 |
|---|---|---|
| 1 | **51 根本跑不了** | 8KB Flash / 512B RAM；Mosquitto 需几十 MB。真跑起来的是它旁边那块 C3，51 不参与 —— 名不副实，成本也不省 |
| 2 | **烧程序即断网** | STC-ISP 靠串口复位下载，每次烧录 51 必重启。它当 broker ⟹ "调代码"与"全家在线"互斥 |
| 3 | **单点故障** | 5V 供电、有复位键、调试时随手可重启；broker 需要的是"装上就别管" |
| 4 | **C3 内存吃紧** | 每 MQTT 连接占缓冲，TLS 每连接 30–40KB；10 节点 + 桥接后余量很小，表现为随机掉线（最难查的 bug） |

**broker 载体的优先级**（按"手上已有什么"排）：

| 优先级 | 载体 | 成本 | 说明 |
|---|---|---|---|
| **1** | 能刷 OpenWrt 的路由器 | 0 | 本就 7×24 常开、功耗约 5W，装 mosquitto 即可 —— 最优雅 |
| 2 | 闲置旧手机（Termux） | 0 | 自带电池＝天然 UPS；但安卓会杀后台需 wake lock，长期插电有电池鼓包隐患 |
| 3 | 树莓派 Zero 2 W | ~150 元 | 最省心，可顺带跑 Home Assistant 一并解决 M6 |
| 4 | 专用 ESP32-S3（带 PSRAM） | ~30 元 | 便宜小巧，TLS 下内存仍紧 |
| 5 | 云 broker | 免费额度 | 只承担异地那一半，不做家里主力 |

> **本决策同样不阻塞 M1**：M1 用 BLE 直连，压根不需要 broker。

## 5. 通信四层降级（节点自动选路）

节点上电后按优先级自动选路，**不需要用户手动切换**：

| 层 | 通道 | 触发条件 | 依赖 |
|---|---|---|---|
| 1 | BLE 直连 | 手机已配对并在范围内 | 无（不需要路由器） |
| 2 | WiFi AP 直连 | 有客户端连上节点的热点 | 无（节点自己当 AP） |
| 3 | 局域网 MQTT | STA 已连 + 本地 broker 可达 | 路由器 + broker |
| 4 | 云端 MQTT | 公网 broker 可达 + 穿透正常 | 外网 |

**设计原则：上层的缺失永远不影响下层可用。** 云端挂了，局域网还在；路由器挂了，蓝牙还能控；手机没电，面板按键还在。

## 6. 节点契约

### 6.1 设备 ID

```
<类型码><两位序号>          例：L01 / C01 / F01 / S01 / P00（中控面板）

L 灯 / LED        C 窗帘（步进）    F 风扇 / 继电器负载
S 传感器组         P 中控面板        X 预留
```

`home_id` 区分不同地点：`h01`（家）、`h02`（老家）——这样异地多宅在同一 broker 下也不打架。

### 6.2 内部协议：UART 行协议（51 ↔ C3，仅中控形态）

```
上行（51 → C3）：  <id>;<KEY>=<VAL>[,...]\r\n
下行（C3 → 51）：  <id>;<CMD>[,<ARG>]\r\n
心跳：            SYS;PING\r\n → SYS;PONG\r\n

例：S01;T=25.3,H=48\r\n    L01;ON\r\n    C01;POS=50\r\n    P00;DISP=ALL\r\n
```

**为什么是 ASCII 行协议**：51 的 256B RAM 装不下 JSON 解析器；ASCII 行一次只处理一行，串口助手直接可读，且换云平台不用改 51 一行代码。

### 6.3 外部协议：MQTT（C3 ↔ broker ↔ 手机）

```
sh/<home>/<device>/cmd     下行指令
sh/<home>/<device>/state   上行状态（retain=true，新客户端一连上就能拿到最新值）
sh/<home>/<device>/online  在线状态（LWT 遗嘱消息，掉线自动发 0）
sh/<home>/<device>/cfg     配置下发
sh/<home>/broadcast        广播（全屋关灯、回家模式）
```

载荷：

```json
{"v":1,"d":"C01","cmd":"POS","arg":"50","ts":1730900000}
{"v":1,"d":"S01","st":{"t":25.3,"h":48,"smoke":0,"pir":1},"ts":1730900000}
```

### 6.4 节点差异化：配置，不是代码

```c
/* node_config.h —— N 个节点唯一的差别就是这几行 */
#define HOME_ID     "h01"
#define DEVICE_ID   "C01"
#define LINK_IMPL   link_gpio      /* 纯节点用它；中控用 link_serial */
#define WIFI_SSID   "xxx"
```

> **分布式在软件上的本质是配置差异，不是代码差异。** 同一份 bin 烧 N 遍，改 ID 即可。

## 7. 双 MCU 分工（中控形态）

```
┌─────────────────────────────┐        ┌──────────────────┐
│  51 (STC89C52RC)            │        │  C3              │
│  · LCD1602 显示全屋状态      │ UART   │  · WiFi / BLE     │
│  · 实体按键 K3/K4            │←──────→│  · MQTT 收发      │
│  · 本地联动规则（断网生效）   │ 行协议 │  · OTA 升级       │
│  · 蜂鸣器报警                │        │  · 心跳 / 重连     │
└─────────────────────────────┘        └──────────────────┘
        ↑ 不知道 WiFi 存在                    ↑ 不知道 LCD 是什么
```

**边界铁律：51 不懂网络，C3 不懂屏幕。** 谁越过这条线，架构就开始腐烂。

## 8. 目录结构

```
firmware/
├── nodeESP/                # ★ 主战场：节点固件（C3）
│   ├── net/                #   WiFi STA/AP、BLE、MQTT 客户端

    ├── bsp/                #   引脚、延时、串口、软件 I2C
    ├── driver/             #   LCD1602、按键、蜂鸣器、DS18B20

    └── app/                #   面板 UI + 本地联动
host/app/                   # 手机端 / PyQt5 上位机
docs/  hardware/
```

## 9. 数据流全景（形态 C+，一次开窗帘）

```
手机 (4G)
  │ MQTT publish  sh/h01/C01/cmd  {"cmd":"POS","arg":"50"}
  ↓
云端 broker
  ↓
窗帘节点 C3        ── 解析 JSON → 转行协议 C01;POS=50 ──→ (link_gpio: 直接驱动步进)
  │                                                       (link_serial: 发给 51)
  ↓ MQTT publish  sh/h01/C01/state  {"st":{"pos":50}}
云端 broker  →  手机收到（灯已到位）
             →  51 面板的 C3 收到 → C3 转行协议 P00;DISP=... → 51 刷 LCD
```

同一条链路，51 只是"顺便也被通知到"的一个订阅者。它不参与转发。

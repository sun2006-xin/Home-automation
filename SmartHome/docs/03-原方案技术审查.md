# 03 · 原方案技术审查

**审查对象**：《51智慧家居.docx》（普中A2 四阶段迭代式智能家居系统，1849 段，含完整驱动代码与验收清单）
**审查日期**：2026-11-07
**结论**：方案骨架扎实、驱动代码可直接用，但存在 **8 处会在实机上翻车的设计问题**，其中 2 处是"按文档做必然失败"级别。

---

## 总评

| 维度 | 评价 |
|---|---|
| 硬件选型 | 合理，普中A2 资源利用充分 |
| 驱动代码 | 可用，模块化程度高，命名规范统一 |
| 阶段划分 | 优秀 —— 迭代节奏清晰，每阶段有独立成果 |
| **资源规划** | **不合格** —— 引脚与串口复用未做全局核算 |
| 云平台方案 | 能跑通，但绑定单平台、免费额度会撞墙 |
| 工程化 | 缺失 —— 无重连、无心跳、无 OTA，节点装进墙里就升不了级 |

---

## 问题 1｜串口独占冲突（阻断级 ⛔）

**原文**：
- 阶段一：`HC-05 TXD → P3.0 (RXD)`、`RXD → P3.1 (TXD)`
- 阶段四：`ESP8266 TXD → P3.0 (RXD)`、`RXD → P3.1 (TXD)`

**问题**：STC89C52RC 只有 1 个 UART。蓝牙与 WiFi 模块抢同一对引脚，**两个阶段无法共存**。做完阶段四，阶段一的蓝牙功能必然失效。

**修正**：
1. 蓝牙不再接 51，改由 **ESP32-C3 提供 BLE**（WiFi + BLE 双模一颗芯片解决）。
2. 51 的 UART 永久独占给 ESP 节点，写死在 `bsp_uart.c` 里，不允许其他模块申请。
3. 若坚持用 HC-05：**放弃蓝牙与 WiFi 共存**，把 HC-05 只当下载/调试口，产品功能里不出现。

---

## 问题 2｜引脚复用未做全局核算（阻断级 ⛔）

| 冲突 | 原文写法 | 后果 |
|---|---|---|
| P2.5/P2.6/P2.7 | LED1–LED8 = P2.0–P2.7；LCD RS/RW/E = P2.6/P2.5/P2.7 | LCD 与 LED5–7 互相干扰，必现闪烁 |
| P3.0/P3.1 | K1–K4 = P3.0–P3.3；串口 = P3.0/P3.1 | 按键电平注入串口，通信乱码 |
| P3.5/P3.7 | DS1302 / DS18B20 / XPT2046 三方共用 | 传感器读数随机失败（原文已警告但无方案） |

**修正**：改用 **I2C LCD1602（PCF8574）** + 仅用 **K3/K4** 作按键 + **去掉 DS1302**（时间由 ESP 经 NTP 下发）。详见 docs/02 第 2.3 与第 3 节。

---

## 问题 3｜MQ-2 走 XPT2046 ADC 不划算（体验级）

**问题**：XPT2046 是触摸屏控制器，与板载触摸屏共用 SPI；MQ-2 需预热 20 分钟，模拟量漂移大，阈值难标定。调试成本高于收益。

**修正**：用 MQ-2 模块自带比较器的 **DO 数字输出**，接普通 IO。先在数字量上把"能报警"跑通，需要趋势曲线时再上 ADC。

---

## 问题 4｜AT 指令方案在 51 上很脆（稳定性级）

**问题**：
- 9600bps 下拼 AT 指令字符串，`UART_BUF_SIZE = 32` 对这种长指令（`AT+CIPSEND=0,20` + payload）余量很小。
- 长连接靠"发完就不管"，**没有心跳、没有重连状态机**。WiFi 抖动一次，设备永久离线。
- 51 的 `main` 是轮询 + `Delay_ms()`，长延时期间串口中断虽然还在收，但没人处理，**极易丢包**。

**修正**：
1. 51 **不再拼 AT 指令**。51 只发行协议（`L01;ON`），AT/MQTT/TLS 全交给 ESP 侧固件。
2. 51 主循环禁止出现 `Delay_ms(>10)`，全部改为非阻塞状态机 + 定时器计数。
3. ESP 侧实现心跳（30s）与指数退避重连（2s→4s→8s，上限 60s）。

---

## 问题 5｜云平台单点绑定（架构级）

**问题**：全部逻辑依赖巴法云。

- 巴法云**免费版限制约 10 设备 / 10 主题**，v2 做多节点会直接超限（付费约 ¥9/设备/月起）。
- 平台非开源，无组态能力，数据与可用性均不可控。
- 一旦平台改政策或停服，项目归零。

**修正**：
1. 引入 `cloud_port.h` 抽象层（见 docs/01 第 4 节），巴法云只是其中一个实现。
2. 节点数超过 5 个时，切 **自建 Mosquitto + 内网穿透**（frp / Cloudflare Tunnel / Tailscale）。
3. **异地访问的真实解法不是云平台，是内网穿透 + 自建 broker** —— 这也是 v2 最有含金量的技术点。

---

## 问题 6｜缺失本地自治（设计哲学级）

**问题**：原方案所有远程功能都以"云在线"为前提。**网一断，系统退化成一个只能按键的灯**。

**修正**：明确写入设计原则 —— **本地控制永不依赖云端**。传感器联动（温度超阈值开风扇）必须在 51 本地判断，云端只负责"通知"和"远程干预"。

> 这条也是业界共识：life-safety 类联动（漏水关阀、高温断电）绝不能走云 API。

---

## 问题 7｜无 OTA（运维级）

**问题**：分布式节点装进墙盒、吊顶后，无法再插 USB 升级。

**修正**：ESP 侧固件从 v2 起必须支持 OTA（ArduinoOTA 或 HTTP 拉 bin）。这是"能不能真的部署多节点"的分水岭。

---

## 问题 8｜验收标准偏"演示"，缺"故障"验证（质量级）

**原文验收清单**全是正向用例（能开灯、能报警、能语音控制），没有一条故障用例。

**修正**：验收清单补一半反向用例：

| 反向用例 | 期望 |
|---|---|
| 拔掉路由器网线 | 本地按键仍可控，30s 内 ESP 进入 RETRY |
| 断电重启节点 | 60s 内自动重连，状态上报正确（retain 恢复） |
| 拔掉一个节点电源 | 其他节点与云端均不受影响 |
| 连续快速下发 20 条指令 | 无丢帧、无死机 |
| 串口注入乱码 | 帧解析丢弃，不崩溃（有帧头/校验） |
| 手机在 4G 网络下控制 | 响应 < 2s |

## 对原方案的保留部分（值得直接沿用）

✅ 四阶段迭代的划分方式 —— 节奏好，每阶段都有可演示成果
✅ Driver 层的文件切分与命名（`drv_xxx.h/.c`）—— 直接沿用，只加 `drv_` 前缀
✅ 各传感器的初始化时序（DS18B20 复位/存在脉冲、XPT2046 读时序、步进电机四相八拍表）
✅ 元器件采购清单 —— 基本正确，只需按本节修正项增减
✅ 简历亮点的写法 —— 措辞不错，M5 完成后再按 v2 改写（"分布式多节点 + 内网穿透异地访问" 比 "接入天猫精灵" 硬得多）

## 修正后的行动差异汇总

| 原方案 | 修正后 |
|---|---|
| HC-05 接 51 串口 | 51 串口独占给 ESP；BLE 由 ESP32-C3 提供 |
| 裸 LCD1602 占 P2.5–P2.7 | I2C LCD1602（PCF8574），释放 3 引脚 |
| K1–K4 全用 | 只用 K3/K4 |
| DS1302 提供时间 | 去掉，ESP 经 NTP 下发 |
| MQ-2 走 XPT2046 ADC | 走 DO 数字量 |
| 51 拼 AT 指令 | 51 只发行协议，AT/MQTT 在 ESP 侧 |
| 巴法云写死 | `cloud_port` 抽象层，可切自建 broker |
| 正向验收 | 正向 + 反向各一半 |
| 无 OTA | v2 起支持 OTA |

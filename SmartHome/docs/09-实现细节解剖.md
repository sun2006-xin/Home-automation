## 0. 先看一张图：四套方案在解决同一个问题

所有智能家居平台都在回答一句话：**"如何让一个陌生的 App 知道怎么控制一台陌生的设备？"**

| 方案 | 抽象单位 | 谁定义 | 特点 |
|---|---|---|---|
| **MIoT-Spec**（米家） | 设备 → 服务 → 属性/方法/事件 | 小米云端 spec 库 | URN 全局唯一命名，能力写在云端 |
| **Matter** | 节点 → 端点 → 簇 → 属性/命令/事件 | CSA 标准 | 簇 ID 固化，跨品牌互通靠认证 |
| **HA MQTT Discovery** | 实体（entity） | 设备自己声明 | 发一条 retain JSON 就自动注册 |
| **BLE 配网 GATT** | 服务 → 特征 | 各家自定义 | 只解决"第一次连网"，4 个特征够了 |

记住一件事：**它们的层次结构几乎同构**（容器 → 分组 → 键值对 → 动作）。
所以我们只要理解其中一套，其余都是方言。

## 1. 米家 MIoT-Spec：用 URN 给每个能力起"全球唯一的名字"

### 1.1 URN 的结构

```
urn:miot-spec-v2:<类型>:<名称>:<十六进制ID>:<厂商.型号>:<版本>
                │      │       │            │          │
                │      │       │            │          └ 1
                │      │       │            └ zhimi.airpurifier.ma4
                │      │       └ 00000001
                │      └ power
                └ device / service / property / event / action
```

实例：

```
设备：urn:miot-spec-v2:device:air-purifier:00000001:zhimi.airpurifier.ma4:1
服务：urn:miot-spec-v2:service:fan-control:00000001:zhimi.airpurifier.ma4:1
属性：urn:miot-spec-v2:property:power:00000001:zhimi.airpurifier.ma4:1
事件：urn:miot-spec-v2:event:alert:00000007
```

**关键洞察**：`property:power` 这个名字是**标准化的**，不是某个厂商自己起的。
所以任何 App 看到 `power` 就知道它是开关，不用为每个型号写驱动。

### 1.2 五类实体与编号

| 实体 | 编号 | 说明 |
|---|---|---|
| 设备 device | — | 顶层，一个物理产品 |
| 服务 service | **siid** | 功能分组，如"风扇控制"、"环境" |
| 属性 property | **piid** | 可读/可写/可通知的状态值 |
| 方法 action | **aiid** | 可调用的动作 |
| 事件 event | **eiid** | 设备主动上报 |

siid / piid / eiid / aiid **均为十进制三位整数**（如 `002`、`001`）。

> 在 Home Assistant 的米家集成里，实例代码长这样：
> `service:002:property:001:valuelist:000` = "待机中"

### 1.3 属性的完整字段定义

这是整套 spec 最核心的部分：

| 字段 | 必填 | 说明 |
|---|---|---|
| `type` | ✅ | URN 表达式 |
| `description` | ✅ | 纯文本描述 |
| `format` | ✅ | 数据类型 |
| `access` | ✅ | 数组：`read` / `write` / `notify` 的组合 |
| `value-range` | 可选 | 整型/浮点：`[min, step, max]` |
| `value-list` | 可选 | 整型枚举：`[{"value":0,"description":"..."}]` |
| `unit` | 可选 | 单位（见下表） |
| `max-length` | 可选 | 仅 string |

**format 支持的类型：**

```
bool  uint8  uint16  uint32  int8  int16  int32  int64  float  string  hex
```

**unit 的枚举值（节选）：**

```
percentage  celsius  seconds  minutes  hours  days  kelvin  pascal
arcdegrees  rgb  watt  litre  ppm  lux  mg/m3
```

> 注意：**单位是 spec 的一部分**。Matter 的教训（见第 4 节）说明，单位与刻度不一致是互操作测试最常见的失败点。

### 1.4 事件的定义

```json
{
  "type": "urn:miot-spec-v2:event:alert:00000007",
  "description": "Alert Alert Alert",
  "arguments": [2, 4]
}
```

`arguments` 是**同一服务内的 piid 数组** —— 意思是"这条事件上报时，会同时带上 piid=2 和 piid=4 的值"。

### 1.5 一个完整设备的 spec 长什么样

下面是我按官方字段规范**重构**的一个智能窗帘 spec（结构真实，ID 为示意）：

```json
{
  "type": "urn:miot-spec-v2:device:curtain:0000A00F:demo-vendor:c01:1",
  "description": "Smart Curtain",
  "services": [
    {
      "iid": 1,
      "type": "urn:miot-spec-v2:service:device-information:00007801:demo-vendor:c01:1",
      "description": "Device Information",
      "properties": [
        {"iid": 1, "type": "urn:miot-spec-v2:property:device-manufacturer:00000001:demo-vendor:c01:1",
         "description": "Manufacturer", "format": "string", "access": ["read"], "max-length": 32},
        {"iid": 2, "type": "urn:miot-spec-v2:property:device-model:00000002:demo-vendor:c01:1",
```

### 1.6 新一代 MIoT 的读写方法

```json
// 读属性
{"id": 1, "method": "get_properties", "params": [{"did":"C01","siid":2,"piid":2}]}

// 写属性
{"id": 2, "method": "set_properties", "params": [{"did":"C01","siid":2,"piid":3,"value":50}]}

// 调方法
{"id": 3, "method": "action", "params": {"did":"C01","siid":2,"aiid":1,"in":[]}}
```

> 对比老 miIO 的 `get_prop` / `set_bright` 这种"每设备一套方法名"，MIoT 的 `get_properties` / `set_properties` **全设备通用** —— 这就是"服务化"的价值：**方法名不需要为每个型号重新定义。**

## 2. miIO 局域网协议：字节级全解剖

### 2.1 报文 32 字节头

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | magic | 固定 `0x2131` |
| 2 | 2 | length | 32 + 密文长度 |
| 4 | 4 | unknown | 通常 `0x00000000`（hello 包里是 `0xFFFFFFFF`） |
| 8 | 4 | device id | 设备唯一 ID（来自 hello 回复） |
| 12 | 4 | stamp | 设备运行秒数 |
| 16 | 16 | checksum | MD5（hello 包里为 `0xFF×16`） |
| 32 | n | payload | AES-128-CBC 密文 |

全部大端序。

### 2.2 加解密与校验

```python
token    = bytes.fromhex(<32位十六进制字符串>)   # 16 字节
key      = MD5(token)
iv       = MD5(key + token)
payload  = AES128_CBC_encrypt(key, iv, PKCS7(json_bytes))
checksum = MD5(header[0:16] + token + payload)
```

固件里的等价做法：**把 token 写进 checksum 字段 → 对整个包做 MD5 → 把结果覆盖回 checksum 字段。**

### 2.3 一次完整的握手 + 开灯

```
① 发 hello（32 字节，无需加密）：
   21 31 00 20 ff ff ff ff ... ff   (共 32 字节)
② 设备回（32 字节，仅头部）：
   bytes 8..11  = device id
   bytes 12..15 = stamp（运行秒数）
   bytes 16..31 = ff×16（新版固件拒绝返回 token）
③ 请求：stamp = hello_stamp + 1 + 已过秒数
   载荷：{"id":4711,"method":"set_properties","params":[...]}
④ 设备回同样的加密包，校验方式相同
```

### 2.4 三条实战坑（官方文档不会写）

| 坑 | 说明 |
|---|---|
| **每次请求前重做 hello** | stamp 与设备运行时间绑定，设备重启后旧 stamp 会被丢弃。重做 hello 很便宜，能避免莫名其妙的超时 |
| **id 要从随机值开始递增** | 设备会缓存最近的请求 id，重复 id 会返回缓存结果或直接不回。从 1 开始会撞车 |
| **一次只能有一个请求** | 设备侧没有连接状态，只有短期的 id 缓存。并发请求会乱 |

### 2.5 那个著名的安全教训

早期固件在 hello 回复的 bytes 16..31 **明文返回 token**，而 hello 不需要任何认证。
结果：**同一局域网内任何人发一个 32 字节包，就能拿到你家所有设备的控制凭证。**

> 所以我们的原则很简单：**握手包里永远不放凭证；不自己发明加密；用现成的 TLS + 账号 + ACL。**

## 3. Matter：簇（Cluster）是"能力包"

### 3.1 四层结构

```
Node（一个物理设备）
 └ Endpoint（功能分区，Endpoint 0 是根）
    └ Cluster（能力包，按功能切分）
       ├ Attribute（状态，可读/可写/可订阅）
       ├ Command（动作）
       └ Event（带时间戳的历史记录）
```

**Endpoint 0 是雷打不动的根**，挂的是"后勤"：基础信息（厂商、型号、固件版本）、网络管理、OTA、访问控制。真正的业务能力从 **Endpoint 1** 开始。

一个带 USB 的智能排插：主路五孔 = Endpoint 1，USB = Endpoint 2，两个分区独立开关。
**在协议看来，这是一台房子里的两个房间。**

### 3.2 常用簇（记这张表就够）

| 簇 | ID | 关键属性 | 典型设备 |
|---|---|---|---|
| OnOff | `0x0006` | OnOff、OnTime | 灯、插座、开关 |
| LevelControl | `0x0008` | CurrentLevel（0–254）、MinLevel | 调光灯、窗帘 |
| ColorControl | `0x0300` | CurrentHue、CurrentSaturation | 彩灯 |
| TemperatureMeasurement | `0x0402` | MeasuredValue（int16，0.01℃） | 温度传感器 |
| OccupancySensing | `0x0406` | Occupancy | 人体传感器 |
| DoorLock | `0x0101` | LockState、LockType | 智能门锁 |
| WindowCovering | `0x0102` | CurrentPositionLiftPercent100ths | 窗帘 |

### 3.3 一个调光灯的完整结构

```
Node
├── Endpoint 0 (root)
│   ├── BasicInformation (VendorName="Acme", ProductName="Bulb C3")
│   ├── Descriptor (PartsList=[1,2])
│   └── NetworkCommissioning
├── Endpoint 1 (Dimmable Light)
│   ├── OnOff        (attribute OnOff=false, command Toggle)
│   ├── LevelControl (attribute CurrentLevel=128)
│   └── Identify
└── Endpoint 2 (Temperature Sensor)
    └── TemperatureMeasurement (attribute MeasuredValue=2350 → 23.50℃)
```

**设备类型（Device Type）就是"必须实现哪些簇"的模板**：
"可调光灯" = 必须实现 OnOff + LevelControl + Identify。这样控制器不用问，一看设备类型就知道有哪些能力。

### 3.4 两个必须记住的刻度约定

| 坑 | 正确做法 |
|---|---|
| **LevelControl 的 CurrentLevel 是 0–254** | 不是 0–255！**255 是保留值**，表示"上一次非零值"（记忆功能） |
| **温度用 int16 表示 0.01℃** | 23.50℃ 要上报 `2350`，不是 `23` 也不是 `235` |

> 原文说法很直白：**"把这些单位搞错是互操作测试里最常见的失败点。"**

### 3.5 配网流程（Commissioning）

```
1. 设备上电，开 BLE 广播
2. 用户扫设备/包装上的二维码（含 setup PIN + 厂商信息）
3. 手机通过 BLE 连上设备
4. 通过 SPAKE2+ 做密码认证密钥交换（PIN 只有设备上印着）
5. 手机把网络凭证发给设备：
   - WiFi 设备 → SSID + 密码
   - Thread 设备 → Thread 网络密钥
6. 设备加入网络，用 mDNS 广播自己
7. 设备出示 DAC 证书链，控制器验证（防山寨）
8. 控制器签发 NOC 证书，设备加入 fabric
9. 后续可 multi-admin：一台设备同时被 Apple/Google/Alexa 控制
```

**核心机制**：`fabric` = 信任域。同一 fabric 内的设备互信，因为证书都出自同一个 CA。

## 4. Home Assistant MQTT Discovery：最省事的自动注册

### 4.1 原理一句话

**设备自己往 `homeassistant/<类型>/<id>/config` 发一条 retain 的 JSON，HA 收到就自动创建实体。**
不用改 HA 代码，不用写 YAML。

### 4.2 一个开关的完整报文

```
主题：homeassistant/switch/irrigation/config       （必须 retain）
载荷：
{
  "name": "Irrigation",
  "command_topic": "homeassistant/switch/irrigation/set",
  "state_topic": "homeassistant/switch/irrigation/state",
  "unique_id": "irr01ad",
  "device": {
    "identifiers": ["garden01ad"],
    "name": "Garden"
  }
}
```

HA 收到后做三件事：
1. 创建实体 `switch.irrigation`
2. 订阅 `.../state` 拿状态显示
3. 用户点击时向 `.../set` 发 `ON` / `OFF`

### 4.3 缩写与基础主题（省流量的写法）

```json
{
  "~": "homeassistant/switch/irrigation",
  "name": "garden",
  "cmd_t": "~/set",
  "stat_t": "~/state"
}
```

| 缩写 | 全称 |
|---|---|
| `~` | 基础主题（后续可写 `~/xxx`） |
| `cmd_t` | command_topic |
| `stat_t` | state_topic |
| `avty_t` | availability_topic |
| `uniq_id` | unique_id |
| `dev` | device |
| `ids` | identifiers |
| `pl_on` / `pl_off` | payload_on / payload_off |
| `stat_cla` | state_class |

### 4.4 灯（JSON schema）与可用性

```json
{
  "~": "homeassistant/light/kitchen",
  "name": "Kitchen",
  "uniq_id": "kitchen_light",
  "cmd_t": "~/set",
  "stat_t": "~/state",
  "schema": "json",
  "brightness": true,
  "avty_t": "homeassistant/light/kitchen/availability",
  "pl_avail": "online",
  "pl_not_avail": "offline"
}
```

状态载荷是 JSON：`{"state": "ON", "brightness": 255}`

**`avty_t` + LWT 的意义**：设备掉线时 broker 自动发 `offline`，UI 立刻显示"不可用"。
> 这解决了一个很隐蔽的问题：**幽灵设备** —— 设备早就离线了，App 还显示在线、还能点，点了没反应。

### 4.5 这一套为什么值得我们抄

| 优点 | 说明 |
|---|---|
| 零代码接入 | 我们的节点只要多发布一条 config 主题，就能直接出现在 Home Assistant 里 |
| 约定优于配置 | 主题路径即语义 |
| 状态与指令分离 | state_topic / command_topic 各管一件事 |
| 可用性内建 | 靠 LWT，不需要额外心跳逻辑 |
| 支持大量设备类型 | switch / light / sensor / cover / climate / lock / fan… |

## 5. BLE 配网：GATT 就四个特征

BLE 在智能家居里主要干一件脏活：**解决"设备不知道 WiFi 密码"的先有鸡还是先有蛋问题。**
一旦拿到凭证存进 NVS，之后每次开机直连，BLE 就不再需要了。

### 5.1 三种实现方案对比

| 方案 | 特征设计 | 编码 | 优点 | 缺点 |
|---|---|---|---|---|
| **Espressif protocomm** | prov-session / prov-scan / prov-config / proto-ver | **Protobuf** + 会话加密 | 官方成熟、有扫描 AP 功能、安全握手完善 | 依赖 IDF 组件，稍重 |
| **Zephyr 示例** | SSID / Password / Security / Control / Status | 裸字节 + 枚举 | 极简、清晰 | 功能少（无 AP 扫描） |
| **自制最简版** | SSID / PASS / CMD / STATUS | UTF-8 文本 | 最容易调，nRF Connect 就能测 | 没加密，仅适合自用 |

### 5.2 Zephyr 版的结构（最推荐照抄）

所有特征共享一个 128 位基础 UUID，短标识替换中间四位：

| 特征 | 属性 | 载荷 |
|---|---|---|
| SSID | write | UTF-8，最长 32 字节 |
| Password | write | UTF-8，最长 64 字节 |
| Security | write | 1 字节枚举（0=Open, 1=WPA2, 3=WPA3…） |
| Control | write | 1 字节：`0x01`=CONNECT，`0x02`=ERASE |
| Status | read + notify | 1 字节枚举：CONNECTING / CONNECTED / FAILED |

**状态机只有四个态**（另一份开源固件的设计，非常干净）：

```
BLE_OFF        初始化前（瞬态）
BLE_ADVERTISING 等手机来（未配网，或已配网但 WiFi 掉了）
BLE_CONNECTED   手机正连着
BLE_PAIRED      WiFi 已通（正常工作态，BLE 转为被动）
```

### 5.3 三个实操细节

| 细节 | 说明 |
|---|---|
| **MTU 设到 517** | 默认 23 字节装不下长 WiFi 密码，一次写不进去就会失败 |
| **启动先试存好的凭证** | 先 `tryStoredWifi()`，成功就直接用，不要每次都等 BLE |
| **失败要有超时** | WiFi 关联 10 秒超时，失败推 `WIFI_FAILED` 状态，让手机能重试而不用重新配对 |

## 6. 四套方案横向对比

| 维度 | MIoT-Spec | Matter | HA Discovery | BLE GATT |
|---|---|---|---|---|
| 抽象层次 | 设备/服务/属性 | 节点/端点/簇/属性 | 实体 | 服务/特征 |
| 谁定义能力 | 云端 spec 库 | CSA 标准 | 设备自己 | 各家自定义 |
| 自描述 | 是（读 spec） | 是（读 descriptor） | 是（config 报文） | 否 |
| 跨品牌 | 需接入米家 | **原生互通** | 限 HA 生态 | 不适用 |
| 学习成本 | 中（URN 体系） | 高（认证、证书链） | **低** | 低 |
| 适合个人项目 | 可参照 | 参照思路即可 | **可以直接用** | **可以直接用** |

**结论**：
- **能力模型学 MIoT-Spec**（URN 命名 + format/access/value-range/unit 四件套）
- **结构学 Matter**（端点分区 + 簇是能力包 + 设备类型=必须簇的集合）
- **自动发现学 HA**（retain config 报文，零代码接入）
- **配网学 Zephyr**（四个特征 + 四态状态机）

## 7. 落到我们项目：capability spec v1

### 7.1 设计原则

| 原则 | 来源 |
|---|---|
| 能力名全局统一（不用厂商私名） | MIoT-Spec 的 URN 思路 |
| 能力 = 一组属性 + 一组命令 | Matter 的 cluster |
| 每个属性必须声明类型/范围/单位/读写权限 | MIoT-Spec 的 format/access/value-range/unit |
| 设备自己声明，中枢不改代码 | HA Discovery |
| 报文保持小，节点 RAM 有限 | 我们的 C3 约束 |

### 7.2 四种能力定义（v1 冻结）

```json
{
  "switch": {
    "props": {
      "on": {"fmt":"bool","access":"rwn"}
    },
    "cmds": ["set", "toggle"]
  },
  "cover": {
    "props": {
      "pos":    {"fmt":"uint8","min":0,"max":100,"unit":"%","access":"rwn"},
      "moving": {"fmt":"bool","access":"rn"}
    },
    "cmds": ["set", "stop", "open", "close"]
  },
  "dimmer": {
    "props": {
      "on":    {"fmt":"bool","access":"rwn"},
      "level": {"fmt":"uint8","min":0,"max":100,"unit":"%","access":"rwn"}
    },
    "cmds": ["set", "toggle"]
  },
  "sensor": {
    "props": {
      "t":     {"fmt":"int16","unit":"0.1C","access":"rn"},
      "h":     {"fmt":"uint8","unit":"%","access":"rn"},
      "smoke": {"fmt":"bool","access":"rn"},
      "pir":   {"fmt":"bool","access":"rn"},
      "lux":   {"fmt":"uint16","unit":"lux","access":"rn"}
    },
    "cmds": []
  }
}
```

`access` 三位：`r` 读 / `w` 写 / `n` 通知。

> **刻度约定（照着 Matter 的坑来定）**：温度用 int16、单位 0.1℃（23.5℃ → `235`）；百分比一律 0–100 整数；布尔一律 0/1 不用 true/false 以省字节。

### 7.3 `_discovery` 完整报文

节点上电（连上 broker 后）往 `sh/h01/_discovery` 发一条 **retain**：

```json
{
  "v": 1,
  "id": "C01",
  "name": "客厅窗帘",
  "type": "cover",
  "fw": "0.3.1",
  "hw": "c3-supermini",
  "caps": ["cover"],
  "props": {
    "pos":    {"fmt":"uint8","min":0,"max":100,"unit":"%","access":"rwn"},
    "moving": {"fmt":"bool","access":"rn"}
  },
  "cmds": ["set","stop","open","close"],
  "topics": {
    "cmd":    "sh/h01/C01/cmd",
    "state":  "sh/h01/C01/state",
    "online": "sh/h01/C01/online"
  }
}
```

中枢只做一件事：**订阅 `sh/h01/_discovery`，把收到的每条报文存进设备表**。新增节点不用改中枢一行代码。

### 7.4 同时兼容 Home Assistant（白捡一个上位机）

节点额外发一条 HA 格式的 config，就能直接在 HA 里出现，省掉 M6 一大半工作量：

```
主题：homeassistant/cover/c01/config                    （retain）
载荷：
{
  "~": "sh/h01/C01",
  "name": "客厅窗帘",
  "uniq_id": "sh_h01_C01",
  "cmd_t": "~/cmd",
  "stat_t": "~/state",
  "avty_t": "~/online",
  "pl_avail": "1",
  "pl_not_avail": "0",
  "dev": {"ids": ["C01"], "name": "客厅窗帘", "mf": "DIY", "mdl": "C3-Node", "sw": "0.3.1"}
}
```

> 注意 HA 的 `cover` 要求状态是 `open`/`closed`/`opening`/`closing` 等字符串，
> 而我们的 `pos` 是数字 —— 需要用 `value_template` / `position_template` 做一次映射。
> 这一步是接入 HA 唯一需要动脑的地方，其余都是照抄。

### 7.5 指令语义（全项目统一，不许各写各的）

| cmd | args | 语义 | 适用能力 |
|---|---|---|---|
| `set` | `{"on":1}` / `{"pos":50}` / `{"level":30}` | 设为指定值 | 全部 |
| `toggle` | 无 | 反转当前状态 | switch / dimmer |
| `open` / `close` | 无 | 全开 / 全关 | cover |
| `stop` | 无 | 停在当前位置 | cover |
| `reboot` | 无 | 重启节点 | 全部 |

**统一语义的好处**：中枢的规则引擎和手机 App 都只需要认这五个动词，不用为每种设备写分支。

### 7.6 与四套方案的对应关系

| 我们的 | MIoT-Spec | Matter | HA |
|---|---|---|---|
| `caps` | service | cluster | 平台类型（switch/light/cover） |
| `props` | property (piid) | attribute | 实体属性 |
| `props[x].fmt/min/max/unit` | format/value-range/unit | 数据类型与刻度 | 单位约定 |
| `access` | access 数组 | 读写权限 | — |
| `cmds` | action (aiid) | command | 服务调用 |
| `_discovery` | 读云端 spec | descriptor | config 报文 |

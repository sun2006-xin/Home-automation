# 07 · 行业调研：米家、Home Assistant、Matter 是怎么做的

> 调研目的：不是抄产品，是抄**结构**。看成熟系统怎么分层、怎么选通信方式、怎么定义设备能力，然后把能用的搬进我们两个项目。

---

## 1. 米家的三层架构

```
小米 AIoT 云（账号、远程中转、OTA、语音）
        ↕
中枢 / 网关层（主中枢、备中枢、从网关、盲网关）
        ↕
终端设备（WiFi 设备 / BLE 设备 / BLE Mesh 设备 / 存量 Zigbee 设备）
```

### 1.1 最值得学的：网关的四种身份

米家把网关分了四个等级，这是一个非常实用的可靠性设计：

| 身份 | 能力 | 断外网后 |
|---|---|---|
| **主中枢** | 本地自动化核心。规则**存在本地**，调度全屋设备 | 照常工作 |
| **备中枢** | 备份。主中枢断电后自动重新选举，接管其工作 | 接管后照常 |
| **从网关** | 接受中枢调度，其子设备纳入中枢系统 | 照常 |
| **盲网关** | **只和云端通信**，不接受中枢调度 | **子设备全部失效** |

**「盲网关」是这份调研里最重要的一条反面教材。**

它描述的正是一个"只会连云、没有本地通道"的设备。米家官方文档甚至直接建议：有中枢的家庭应当关闭盲网关的网关功能。

> **对我们的直接意义**：任何节点如果只有"连云"这一条路，它就是个盲网关。所以我们的节点必须有 BLE 直连 / WiFi AP / 局域网 broker 至少一条本地通道 —— 这不是锦上添花，这是区分"能用"和"能用十年"的分水岭。

### 1.2 主备选举我们不做，但用"中枢可替换"替代

主备选举需要心跳、仲裁、状态同步，成本很高。个人项目不必做。但可以用一个更便宜的办法达到相似效果：

> **中枢上不存任何不可重建的东西。**
> 规则写成 JSON 文件、设备清单来自 MQTT 自动发现、历史数据定期导出。
> 中枢坏了 → 换个设备装上 broker + 规则文件 → 十分钟恢复。

这比选举简单得多，可靠性收益却拿到了八成。

## 2. 通信方式选型：不是所有设备都该用 WiFi

| 技术 | 米家的用法 | 解决的问题 | 我们的对应 |
|---|---|---|---|
| **WiFi** | 常供电设备：空调、吸顶灯、摄像头、扫地机 | 带宽大、直连路由器 | 节点主通道（M2 起） |
| **BLE** | 电池设备：传感器、门锁、手环 | 极低功耗 | 节点近场直控 + 配网（M1） |
| **BLE Mesh** | 大量低功耗需组控：灯、开关、插座 | 多对多泛洪、可中继 | ❌ 不做 |
| **Zigbee** | 存量产品，官方已不再推广 | 老生态 | ❌ 不做 |

**关键认知**：一颗 2000mAh 电池的温湿度传感器，用 WiFi 上报大概 3–7 天就没电；用 BLE + 深睡可以撑一年。所以"给每个设备装 WiFi"这个方案，只对**常供电设备**成立。

> **对本项目的约束**：我们的 C3 节点目前都假设"常供电"（电机、灯、风扇本来就要插电）。
> 如果将来加电池传感器，必须切 BLE + 深度睡眠，不能沿用 WiFi 节点固件。这一点写进 docs/06 的"未来扩展"。

## 3. MIoT-Spec：用 ID 描述设备能力

米家把每个设备抽象成四层结构：

```
设备 device
 └ 服务 service (siid)
    ├ 属性 property (piid)   ← 可读可写，如 on / brightness / temperature
    ├ 方法 action (aiid)     ← 可调用，如 toggle / open
    └ 事件 event (eiid)      ← 设备主动上报，如 按键按下 / 故障
```

举例：一个灯 ≈ `service 2 (light)` 下的 `property 1 = on`、`property 2 = brightness`。第三方 App 不需要知道具体型号，只要读 spec 就知道怎么控。

**为什么这个设计厉害**：新增设备类型不用改 App。App 只会"读属性、写属性、调方法"，具体含义由 spec 描述。

> **我们能抄的简化版**：把 `{"cmd":"POS","arg":"50"}` 规范化成"能力名 + 参数"，并在节点上声明自己支持哪些能力（capability）。详见 docs/06 第 5 节的能力模型。

## 4. miIO 局域网协议：UDP + AES，纯本地可控

米家设备的局域网控制协议（第三方逆向出来的，官方从未公开）：

| 项 | 内容 |
|---|---|
| 传输 | **UDP 54321**，无连接，一请求一应答 |
| 包头 | 32 字节：magic `0x2131` + 总长度 + 设备 ID + 运行秒数 + 16 字节 MD5 校验 |
| 载荷 | JSON-RPC（`{"id":4711,"method":"get_properties","params":[...]}`） |
| 加密 | **AES-128-CBC + PKCS#7**，key = MD5(token)，iv = MD5(key ‖ token) |
| 凭证 | 每设备一个 16 字节 token |
| 握手 | 发 32 字节 `21310020` + 28×`ff`，设备回 device_id 与 uptime |
| 云 | **不是必需**。绑定账号才会连云，协议本身完全本地可用 |

### 两条值得借鉴的细节

1. **用设备 ID 寻址，不用 IP。**
   设备 ID 终生不变，而 IP 是 DHCP 给的、随时会变。协议里 id 存在包头里，就是为了换网段后还能找到它。
   → 我们的 `device_id`（L01 / C01）走的是同一条路，不需要知道节点 IP。

2. **握手必须每次请求前重做。**
   因为包头里带的是"设备运行秒数"，设备重启后时间基准就变了，旧 stamp 会被丢弃。
   → 我们的对应经验：**设备重启后所有会话状态都要重建**，不能假设连接还有效。

### 一条明确的教训

早期固件会在 hello 回复里**明文吐出 token**，导致同一局域网内任何人都能读取并控制设备。后来版本才改成 `ff×16` 拒绝返回。

> **教训**：握手包里永远不要放凭证。我们的做法更简单 —— 不发明加密协议，直接用 **MQTT over TLS + 用户名密码 + broker 端 ACL**，把安全交给成熟设施。

## 5. Home Assistant / ESPHome / Matter

| 项目 | 定位 | 该学什么 |
|---|---|---|
| **Home Assistant** | 本地优先的家庭自动化平台，3000+ 集成 | ① `entity + state + attributes` 的状态模型；② automation 的**三段式**：`trigger` / `condition` / `action` |
| **ESPHome** | 用 YAML 声明设备能力，编译出固件 | "配置即固件"。我们 `node_config.h` 就是它的 YAML 等价物 |
| **Matter / Thread** | 跨品牌统一应用层，基于 IP | 设备类型 + cluster/attribute 的标准做法；但认证 6–12 周、$5k–15k，个人项目不值得 |
| **painlessMesh** | ESP 之间的 Mesh 网络 | ⚠️ 反例：ESP8266 做 Mesh 内部节点时只剩 10–13KB 堆，做叶子节点才行 |

**HA 的三段式直接可以作为我们规则引擎的 JSON 结构**：

```json
{
  "name": "烟雾报警开窗",
  "trigger":   {"device": "S01", "attr": "smoke", "op": ">=", "value": 1},
  "condition": [{"device": "C01", "attr": "online", "op": "==", "value": 1}],
  "action":    [{"device": "C01", "cmd": "POS", "arg": "100"}],
  "cooldown_s": 60
}
```

这个结构简单到可以手写，又足够表达绝大多数家庭场景。

## 6. 总结：抄六条，不抄三条

### 值得抄

| # | 设计 | 落到我们哪里 |
|---|---|---|
| 1 | **网关梯队（主/备/从/盲）的思想** | 我们不实现选举，但用"中枢数据可重建"达到同等效果 |
| 2 | **能力模型（service/property）** | docs/06 第 5 节的简化 capability 表 |
| 3 | **ID 寻址，不用 IP** | `device_id` + MQTT 主题，天然做到 |
| 4 | **本地直配（旋钮直接配对灯，不经网关）** | 我们的 BLE 直控，断网仍可用 |
| 5 | **三段式自动化（trigger/condition/action）** | 规则引擎的 JSON 结构，中枢执行 |
| 6 | **双链路（云远程 + 局域网本地）** | 我们的 MQTT bridge + 本地 broker 架构 |

### 明确不抄

| # | 内容 | 原因 |
|---|---|---|
| 1 | BLE Mesh 组网 | 泛洪协议复杂、ESP32 上资源吃紧，我们的场景（每设备常供电）用不着中继 |
| 2 | 自研私有加密协议（miIO 那套） | 逆向维护成本高，且历史上有 token 泄露事故。用 TLS + ACL 就够 |
| 3 | Matter 认证 | $5k–15k、6–12 周，个人开源项目完全不划算 |

---

## 7. 一句话结论

> 米家最值钱的不是它的 App，而是它把**"什么必须本地、什么可以上云"**这条线划得非常清楚：自动化规则在本地，远程访问才走云。
> 它唯一的污点是"盲网关"—— 那正是我们要避免的东西。

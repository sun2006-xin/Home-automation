# SmartHome — 分布式智慧家居系统（项目二）

> 📍 **先读 [`PROJECT.md`](./PROJECT.md) —— 一页看懂整个项目：有哪些东西、各有什么功能、怎么连起来。**
> 本文只讲项目性质与开发约束；细节一律在 PROJECT.md 的文档索引里找。

> 最小单元不是一块板子，而是**一个电器 + 一块 ESP32-C3**。
> 判断放节点、编排放中枢、云只做出口。**本项目不依赖 51 单片机。**

---

## 一句话定位

把每个电器的驱动做成**独立节点**：一块 ESP32-C3 管一个电器，自带蓝牙近场直控、WiFi 局域网组网、云端异地控制三层通道。一台常开设备（旧手机 / 树莓派 / 路由器）当**本地中枢**，同时承担 broker（邮局）与规则编排（调度员）。

## 项目性质（写死，防止自欺）

> **本项目是最大程度模拟，目的是快速验证架构与想法，不是可上市的产品。**
> 全部 12V 直流，**不接 220V**。产品化（安规、EMC、可靠性、3C 认证、量产）是商家的事，那是另一条成本曲线。
> 我们的优势是**快**：几天内跑通一套架构、证伪、再迭代。
>
> **能证明**：拓扑逻辑、通信协议、状态同步、场景编排、故障模式
> **不能证明**：电气安全、负载特性、发热与线径、EMC、安规认证
> 详见 `docs/11-产品与功能设计.md` 第 9.2 节「模拟保真度矩阵」

## 三种部署形态（同一套固件）

```
形态 A  纯节点              形态 B  局域总线            形态 C  中枢 + 异地
┌────────────┐          ┌──────────────┐          ┌──────────────────┐
│ 电器 + C3   │   ───→   │ N×C3 + 中枢   │   ───→   │ + 穿透 + 云端      │
│ 手机 BLE 控 │          │ 手机同网 MQTT │          │ 4G 异地 / 提醒推送  │
└────────────┘          └──────────────┘          └──────────────────┘
   M1 达成                  M3 达成                    M4 达成
```

## 三层决策分工

| 层 | 在哪里 | 管什么 | 断网后 |
|---|---|---|---|
| 层一 | 节点本地（C3） | 同节点内的联动，如本机温度 → 本机风扇 | 照常 |
| 层二 | 本地中枢 | 跨设备编排、定时、场景，如烟雾 → 开窗 | 照常 |
| 层三 | 云端 | 把消息送出家门外，异地访问与推送 | 失效（不影响上面两层） |

> **跨设备的规则必须有人居中协调** —— 因为节点不该知道别的节点存在。这是中枢存在的唯一理由。

## 四条铁律

1. **节点自治**。一个 C3 管一个电器，节点之间不互相依赖；任一节点挂掉，其他照常。
2. **跨设备联动不放进节点**。节点只做自己范围内的判断，跨设备的交给中枢。
3. **本地永远优于云端**。云端是增强不是依赖，断网后蓝牙、按键、中枢编排必须仍可用。
4. **差异靠配置，不靠代码**。N 个节点同一份 bin，只改 `node_config.h` 里的 `DEVICE_ID`。
